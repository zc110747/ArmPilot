### 关键设计点 / 本轮踩坑

- **拖动平面必须冻结**：每帧按当前 TCP 重建平面会形成自反馈环
  （目标变→关节变→TCP 变→平面跟着变），手感「飘走」且永不收敛。
- **越界不钳位**：球壳边界 `[40,200]` 与关节限位**不是同一个约束**，
  钳位会造出「看似合法、真机做不到」的姿态，且让工作空间边界从界面上消失。
- **锁死分量取精确相等**：`snapToMode` 显式设回锚点值，使 `target[2] === anchor[2]`
  成为可断言的**定义**，而非数值巧合。
- **滑杆 / HOME / ZERO 属「非目标驱动」** → 让 `target` 跟随新 TCP 并清空 `ikStatus`，
  否则幽灵标记停在旧位置误报「未到位」。
- **3D 拖动 e2e 必须走 CDP 真实鼠标事件**：`dispatchEvent` 造的 pointer 事件绕不过 R3F 射线拾取。
  已沉淀进 skill `webui-headless-cdp-verify` 的「硬坑 4」。
- **类型收窄**：测试里 `expect(result.success).toBe(false)` 不构成 TS 收窄，读 `result.reason` 报 TS2339；
  加 `if (result.success) throw new Error(...)` 兼作断言失败时的兜底报错。
- `model.joints` 含**固定关节**（`tool`），而 `commandJoints` 只含可动关节 →
  遍历限位断言必须用 `movableJoints()`，否则读到 `undefined`。

### 三条核心设计
1. **回推只写 `actualJoints`**（回环打破）。400 点轨迹用 `toBe` 断言 `commandJoints` **引用从未改变**。
2. **Mock 如实模拟物理约束**：240°/s 有限角速度 + 15ms 延迟 + 可注入丢帧 + 限位拒绝（`ERR JOINT` 且位置不动）。
   不做理想回显的理由写进 D24：理想回显下误差显示 / 收敛 / 丢帧 / 限位四条路径**一条都没被验证**。
3. **尾沿合并 33ms + 结束补发**；`transportDriven` 让 `actual` 的写入者**排他** ——
   接入后命令路径不再写 `actual`，否则 Mock 的滞后回推会被下一次命令立刻覆盖，误差恒 0。

### 踩到的两个坑
- **`dispose()` 先退订 status 监听、再 `transport.disconnect()`** → `disconnected` 事件**没有听众**：
  断开后状态灯仍显示 Connected、Actual 挂着滞后值。改为在 `dispose()` 末尾**显式**
  `setConnection(null, 'disconnected', ...)`，不依赖事件时序。
- **e2e 断言顺序**：原打算先 `poll` 日志（日志 500ms 合并一次），但那时 Mock 早已收敛，
  "滞后"断言必然失败。正确顺序是 **`setSlider` 后立刻 `evaluate`**（CDP 往返 ~5ms < 15ms 延迟），
  再 `poll` 收敛。实测即时读数 `cmd 39.9° / act 0.8°`。

### 顺手修的既有错
`protocol/serial-v1.md` §2 的关节↔舵机映射仍是**早期推定值**（`shoulder→S8 / elbow→S7`），
与 Phase 4.5 实测结论（**S7=肩 / S8=肘**）**正好相反**。这是 Phase 9 固件要照抄的文档，

# Phase 8 · Go WebSocket（真实后端 + 内置假固件）✅

## 落点决策（AskUserQuestion 三项全取推荐）
1. 后端**新建** `MeArm-3D/backend/`（自包含 Go module `armpilot/backend`），**不塞进**
   `MeArm-RemoteControl` —— 那是舵机级摇杆服务（8080），混入关节级逻辑会让"谁负责标定"
   变模糊，而铁律是标定只有 `config/robot.yaml` 一份。端口 **8090**，两者并存。
2. 链路末端用 **Go 内置 sim「假固件」**：走真实字节流（`JR`/`OK JR`/`STATE`），
   只有串口驱动是假的；舵机空间 target/actual + 有限角速度 + 送达延迟 + 硬限位 + 开机静默窗口。
3. 验收含**浏览器真实 WS 端到端**（headless Edge + CDP）。

分层：`wsserver → controller → device(sim|serial)` + `protocol`（编解码）+ `robot`（标定/限位）。
`controller` 是唯一"懂机械臂"处；`wsserver` / `protocol` 都不认识关节语义。

## ★ 本轮最值钱的发现：量化精度就是跟踪误差的下限
e2e 首跑 `Phase 8：跟踪误差统计归零（stat-lag）` **FAIL — 0.02°**。
根因不是机械臂没到位，而是**双方用不同精度表述同一个位置**：
前端内部 `elbow = 112.6185771989`，`JR` 线只保留 1 位小数 → `112.6`，
直接相减恒差 **0.0186°** ⇒ 面板永久显示 `0.02°`、「正在逼近目标」**永不熄灭**。
**这是个假误差**，而它同时出现在 StatusPanel（「滞后 X°」）与 ConnectionControl 两处，是用户可见的。

修法：在 `wsProtocol.ts` 显式声明链路精度并**只量化命令侧**（不量化测量的状态，否则会掩盖真实误差）：
```ts
export const WIRE_JOINT_STEP_DEG = 0.1;
out[id] = Math.round(v * 10) / 10;   // ⚠️ 不能写 Math.round(v / 0.1) * 0.1（0.1 不精确 ⇒ 差 1 ulp
                                     //    ⇒ "误差 0"退化成 1e-14 ⇒ moving 再次永真）
```
同时**更新了一条既有的、不再符合现实的单测**：它把 `jointsAt(30)`（全精度）当成后端回推值，
而后端**永远不可能**回推 112.6185771989 —— 真实回推值是线上值。改为 `onWire()` 包装。

## 其它四条语义（都写进测试）
- **`OK JR` 是目标角，不是实际位置**：只做标定核对（容差 0.1°，告警不阻断）。
  拿它发布状态 ⇒ 误差恒 0。单测有一条专守："ACK 到达**不发布**状态"。
- **ACK 门控 + latest-wins（不排队）**：在途期间新命令只覆盖待发槽。
- **间隔节流禁用 `time.Sleep`**：会卡住读循环（回执靠它消费）⇒ 自锁。
  首版就是踩了这个，表现为"发完第一条就再也收不到回执"。改为撤下在途 + 定时器补发。
- **重连补发当前命令，且只在重连时补**：首次无条件补发会白白占用一次节流窗口，
  打掉 Phase 7 锁定的时序契约（`transport-loop` 阶跃断言立刻失败）。
  e2e 验证方式最直接：杀掉后端 → 重启（新 sim 从 HOME 起步）→ Actual 必须回到 29.9°。

## e2e 新增 21 项断言中踩到的坑
`Phase 8：断开 → 状态灯复原为 Disconnected` **偶发 FAIL**（同一脚本前一轮 PASS）。
判据：按钮在 `busy` 或未连接时是 `disabled`，重连过程中连接态会短暂进入 `connecting`
（界面映射为 "Disconnected"），一次 `click()` 落在这个窗口会被**静默吞掉**。
修法：把**点击与读取放进同一次 `evaluate` 并允许重试**（真断不开时依然失败，不掩盖问题），
失败时输出 `{badge, disabled}` 诊断。改后连跑两轮 **49/49**。
