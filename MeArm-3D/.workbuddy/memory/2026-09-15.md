## CAD→URDF 参数接入方案：评估后放弃（零改动）

**动机**：`robot.yaml` 第 41–42 行自述机构尺寸（base 60 / 大臂 80 / 小臂 80 / 手 40）

**结论：不可用，放弃。** 四条硬证据（全部实读）：

1. **只有 1 个 link、0 个 joint**。`robot.urdf` 全文 82 行，仅 `base_link`，无任何 `<joint>`。

   ⇒ 无 parent→joint→child 树 ⇒ joint origin / rpy / axis / limit 全部**无输入可取**。
2. **被指派的 6 个零件物理上是错的**：part_001(90.7×145×3) / part_002(58×58×3) 薄板，
   part_081/084(5.5×5.5×23) 螺栓，part_108/110(6.4×5.5×2.4) 螺母。
   **大臂、小臂、立柱、两个夹爪、4 个舵机一个都没有**。且无 `<material>`、无颜色。
3. **单位差 1000 倍**：bbox 数值在 155~308（mm），而 `base_origin_xyz` 是
   `[-83.12, 94.21, 258.29]`；URDF 写 `<mesh scale="0.001 0.001 0.001">`（源 STL 是 mm）
   却把原点按 m 写成 0.0831/0.2583 ⇒ **尺寸按 mm 留、原点按 m 写**。
4. **base_origin 与几何不自洽**：整机 bbox Z 最低 155，但这 6 件的 X 只有 −114.5~50.2。

**为什么不该照 URDF 改 `robot.yaml`（即使 URDF 完好）**：
- `robot.yaml` 的限位/零位/标定 offset·scale 已是 **2026-09-12 相机实测反解值**，
  有 COM18 真机链路 PASS 11/11 + 4 份黄金数据交叉验证；只有**尺寸**是标称值。
- **STL 外框量的是零件外形，不是 joint-to-joint 距离**（用户 spec §9 自己也写了这条）。
- 要更新尺寸，唯一合格输入是**标尺实拍**（`docs/hardware-measurement.md` §7 Phase 4.5 台面）。

**纪律确认**：`robot.yaml` 的 kinematics/actuators 受 `freeze_baseline.py` 语义核心哈希守卫；
`links[].geometry` / `details` 是白名单放行的**纯外观层**（D55），可自由换 STL 网格而不碰运动学

### ★ 误判复盘：自研解析器的能力边界 ≠ 数据的缺陷（**这条要长期记住**）

我最初用自研正则解析器读这个文件，得出「110 个装配实例只指向 8 个无几何空容器、
50 个实体全挂在 46 个孤儿 PRODUCT_DEFINITION 上、**0/241** 可达几何」并写成
`BLOCKED` / `Level 0：输入不具备`。**该结论是错的。**

用户指出「不要自己写解析器，使用完整的开源项目，感觉是解析的有问题」——
**用户判断正确**。改用 **OCCT**（`cadquery-ocp`，`STEPCAFControl_Reader` +
`XCAFPrs_DocumentExplorer`）读同一份文件：

```
nodes=111  leaves=103  with_geometry=111  servos=4       ← 111/111 全部有几何
```

自研解析器静默丢弃的**三处**机制（都很隐蔽，修完一处还会被下一处继续骗）：
1. **复合实例语法** `#1385 =( A(...) B(...) C() );` —— 多子类型并列、无单一类型名。
   单类型正则整条**静默跳过**。本文件 **605 个**（= ID 空洞数），含全部装配变换。
   ★ 修好这一处后**实体计数已对齐（154708 / 0 缺失），但几何仍然是 0** —— 说明还有别的坑。
2. **嵌套括号引用**：`FACE_OUTER_BOUND('NONE', (#101436), .T.)` 的环引用嵌在子括号里，
   `refs()` 只处理 str 不处理 list 就漏整条 bound 链。
3. **编码**：名义 ISO-8859-1，法语名（`pieds sous la platine`）+ 中文占位标签交替。

> **铁律**：不要用自研解析器读复杂标准格式（STEP/IGES/DWG/DICOM…）。
> 当自研工具给出**否定性结论**（「文件坏了」「数据缺」）时，**必须先用参考实现复核**，
> 否则会把「工具的能力边界」误报成「数据的缺陷」。
> ⇒ 正确顺序永远是**先 OCCT 复核，再下结论**。

### 为什么 STEP **不能**给出 4 段 `length`（关键，别再试）

- **已证明 STEP 姿态 ≠ 零点位**：yaml 零点位下 shoulder=0（大臂竖直）+ elbow=112.62

- 唯一正当路径仍是**标尺实拍**（`docs/hardware-measurement.md` §7 Phase 4.5）。

### ★★ 关键新事实：`step_report.py` 的 AABB 会把斜置件放大 5 倍（这条要长期记住）

`core/tools/step_report.py` 输出的是 **AABB**（轴对齐包围盒）= 件在世界轴上的**投影范围**，
**不是件自身尺寸**。一块相对世界轴转了 42° 的板，AABB 会大出近一倍。

| 口径 | 件 `17` 三边 |
|---|---|
| AABB（`step_report.py`） | `[40.29, 71.358, 44.229]` |
| **OBB（`Bnd_OBB`）** | `[3.0, 8.0, **88.0**]` |

⇒ Phase 1 起始阶段所有基于 AABB 的尺寸推断**全部作废**。
**新工具 `core/tools/step_obb.py`**（OCCT `BRepBndLib.AddOBB_s`）才是尺寸真值提取器。
用法：`python core/tools/step_obb.py <file.STEP> --json <out.json>` → `nodes=111 plates=94`。

★ **OCCT pybind API 陷阱（会静默失败，必须记住）**：
- `BRepBndLib.AddOptimal_s(S, Bnd_Box)` 造的是**更紧的 AABB**，**不是 OBB**。
  给它 `Bnd_OBB` 会抛异常；我最初 `except: return None` 把异常吞了
  ⇒ **111 个节点全打印 `(no OBB)` 且无任何提示**（正是本项目铁律禁止的静默失败）。
- 有向包围盒的正解是 **`BRepBndLib.AddOBB_s(shape, Bnd_OBB, useTriangulation, isOptimal, useShapeTolerance)`**。
- 教训（与"自研解析器"同源）：**用错口径的测量工具，会把"工具的局限"表现成"数据的性质"。**
