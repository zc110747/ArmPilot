## 补丁：“命令队列满，丢弃”根因 + 流量控制

用户贴日志：快速拖拽摇杆时大量 `命令队列满，丢弃`。根因（两层）：
1. **摇杆高频无合并**：旧 `handleWS` 在每条 `joy` 直接 `WriteLine` 入 FIFO（64 深），
   拖拽峰值每秒数百条 → 队列秒满被丢弃（核心诱因）。
2. **WriteFile 无写超时兜底**：Windows COM 端口即使无设备 `CreateFileW` 也能成功打开，
   但旧 `COMMTIMEOUTS` 写超时=无限；若设备未就绪，`writeLoop` 卡在单次 `WriteFile` 上，
   既不 drain 队列也不报错，窗口内新命令持续堆积。

改动：
- `internal/web/server.go`：摇杆改**最新值合并**（latest-wins）：`pushJoy` 写容量 1 通道，
  `joyPump` 以 20ms 节拍（50Hz）只下发最新位置。拖多快队列也只缓冲 1 条，永不过载；
  未连接时 `WriteLine` 立即返回错误（不入队），不堆积。
- `internal/serial/serial.go`：`writeLoop` 每条指令间保持 `minInterval`（默认 10ms）最小间隔；
  加 `TX` 调试日志（log_level=debug 时打印每条实际下发字节）。
- `internal/config`：新增 `serial.min_interval_ms`（默认 10）。
- `internal/serial/windows_serial.go`：`writeTotalTimeoutConstant` 设 500ms，设备无响应时快速
  失败并触发重连（避免永久阻塞）。
- `internal/tcp/tcp.go`：新增 `[tcp] 透传指令 "..." -> 串口` 日志，便于无设备时也能确认
  “TCP 收到的指令 = 写串口的内容”。
- 新增 `tools/tcp-test.js`：模拟局域网 TCP 设备，发离散指令 + 25 条高频 burst 压测。
- 新增 `config.test.debug.yaml`（COM4 + debug + 10ms 节流）供联机验证。

验证（沙箱 COM4 为无对端虚拟端口，WriteFile 会阻塞到 500ms 超时——**纯沙箱特性**，真实
USB 串口写即返回）：
- `tools/tcp-test.js` 以 ~1ms 间隔连发 25 条 `JOY`，服务器全部正确**透传**，**未出现队列满**。
- TCP 透传日志显示指令字符串与下发内容一致（`STATUS`/`S9=120`/`JOY 7 29 512 512` 等）。
- `go build`/`go vet`/`go test` 全绿。

结论：用户机“队列满”是旧版摇杆直灌 FIFO 所致，已用合并+节流根除；真实硬件写操作立即返回，
10ms 间隔 + 500ms 写超时保证不冲刷、不卡死。

## 补丁：命令-应答（ACK）门控 + 通讯失败界面显示

用户新要求：发送串口命令须等下位机应答后再发下一条；不重复下发；中间指令不需下发；
通讯失败界面要有显示。

先读 `arm-device/core/cmd.c` 确认应答契约：每条合法指令下位机都回一行（`OK SET ...` /
`OK JOY S6=.. S7=.. S8=.. S9=..` / `OK RESET -> 90` / `ERR ...` 等），此即 ACK。

改动（重构 serial 层为命令-应答状态机）：
- `internal/serial/serial.go`：移除旧 `cmdCh` FIFO + `writeLoop`；新增 `ackPump` 状态机：
  空闲时从 joyCh(容量1,latest-wins)/cmdCh(容量16,FIFO) 取一条 `writeOne` 写出 → 置“等待应答”
  + 启动 `ackTimeout` 计时 → 收到设备回显行即视为 ACK（清等待、commOK、发下一条）→
  计时超时 → `setCommErr`（通讯失败，**不重发**、清空待发、等用户下一条）。`WriteLine` 仅把命令
  入对应缓冲（未连接立即报错）。`openPort` 返回类型改为 `io.ReadWriteCloser`（便于测试注入假连接）。
- `internal/config`：新增 `serial.ack_timeout_ms`（默认 800）。
- `internal/web/server.go`：移除旧 `joyPump`/`pushJoy`；joy 与 cmd 均直接 `WriteLine`（合并/门控
  已下沉到 serial 层）。`serverMsg`/`sendStatusTo`/`BroadcastStatus` 增加 `comm_err`/`comm_err_msg`。
  `Status()` 返回四元组 (connected, serialErr, commErr, commErrMsg)。
- `main.go`：串口 `SetLineHandler(h.Broadcast)` 替代旧 `ser.Lines()` 广播循环；`SetStatusHandler`
  四参回调。
- `web/static/js/main.js` + `style.css`：顶栏串口状态三态（未连接红 / 已连接通讯正常绿 /
  已连接但通讯失败琥珀色），通讯失败时顶栏显示“串口: 通讯失败”并终端打印。
- `tcp.go` 日志改 `[tcp] 收到指令 "..."（入待发缓冲）`，与真正写串口的 `[serial] TX`（debug）区分。

测试（关键）：新增 `internal/serial/ack_test.go` —— 用 `dialSerial` 注入 `fakeSerial`（实现
`io.ReadWriteCloser`，Read 从通道取设备应答行，Write 记录字节）。两个单测：
- `TestAckGatingLatestWins`：下发首条→回 ACK→再连发 4 条摇杆（无 ACK）→ 断言仅首条+合并后最新
  共 2 条写出，中间值被丢弃。
- `TestAckTimeoutCommFailure`：下发一条后永不回 ACK → 断言 `commErr=true` 且带原因文本。
两个测试均 PASS，直接证明用户三条要求（等应答、不重发、中间不下发、失败可见）。

`go build`/`go vet`/全量 `go test` 全绿。README 流量控制章节已改写为“命令-应答门控 + 通讯失败显示”。

坑：初版 `ackPump` 的 select 里同时有 `case <-s.joyCh:`/`case <-s.cmdCh:` 直接调 `trySend`，
会把命令从通道**取走**后 takePending 读到空 → 命令丢失。改为仅保留 `case <-s.wakeCh:` 唤醒，
实际取出只由 `takePending` 完成，修复。

## 下位机 arm-device 适配 ACK 门控（修改 + 烧录 + 实测）

用户要求：下位机也修改并下载（烧录），适配“等应答再下发”的门控并测试。

### 关键发现
- `arm-device/core/cmd.c` 每条合法指令本就回一行 `OK ...`/`ERR ...`（即 ACK），但有三处会导致
  门控“永远等不到应答 → 误判通讯失败”：
  1. `SEQ STOP` 在序列未运行时 `ir_seq_stop()` 直接 return **不回任何行** → 该指令无 ACK。
  2. 硬件红外回显 `IR RAW=...` 是**异步事件**，若被门控误判为应答，会在“等待应答”窗口内造成
     假 ACK（用户正好按物理遥控时）。

### 改动
- `arm-device/core/ir_seq.c`：`ir_seq_stop()` 始终回 `OK IRSEQ idle (not running)`（空闲）/
  `OK IRSEQ N stop`（运行中），保证 `SEQ STOP` 恒有应答。**flash 后实测 `SEQ STOP` 空闲回
  `OK IRSEQ idle`**。
- `arm-device/core/ir_seq.c` / `ir_ctrl.c`：硬件红外回显、`IR ? (unbound code)`、摇杆中断序列的
  `IRSEQ stop: joystick` 等**异步事件统一以 `# ` 前缀**标记（如 `# IR RAW=0x...`），明确不是命令应答。
- `arm-web/internal/serial/serial.go`：`ackPump` 改为**任何非 `# ` 开头的回显行即视为应答**；
  `# ` 行仅广播到日志、不清除“等待应答”状态 → 异步事件不会假 ACK。
- `arm-web/internal/serial/windows_serial.go`：**修复 `openPort` 打开串口必失败**：`DataBits`
  缺省为 0 时 `SetCommState` 报“参数不正确”。现 `byteSize<5||>8` 回退为 8 位。

### 构建 / 烧录（沙箱实测）
- 工具链：`~/.platformio/packages/toolchain-atmelavr/bin/avr-gcc` + `~/.platformio/packages/tool-avrdude`。
  （`scripts/build.bat` 写死 `D:\tools\agent-tools`，本机路径不同；用等价手动编译命令经 `~/.platformio`
  工具链构建成功，FLASH 12620B/32256B≈39.1%，RAM 516B/2048B≈25.2%，**零警告 -Wall -Wextra**。）
- 烧录：`avrdude -C <conf> -p atmega328p -c arduino -P COM4 -b 115200 -D -U flash:w:.build/firmware.hex:i`
  → **沙箱 COM4 接真实 Uno（签名 0x1e950f），12620 字节写入并校验通过**。

### 测试
- `tools/host_verify.py COM4 9600` → **67/67 PASS**（真实硬件），含新 `OK IRSEQ idle` 与 `# IR RAW=` 行为。
- Go 单测新增：`TestAsyncLineNotAck`（`# ` 行不误判应答）、`TestSeqStopIdleAcks`（空闲 SEQ STOP 回 OK
  被门控正确识别、不误判通讯失败）；加 `TestRealHardwareAck`（设 `REAL_COM=COM4` 时跑，端到端验证
  web 门控与真实固件联动）。全部 `go test ./internal/serial/ ./internal/protocol/` 通过。
- **限制**：沙箱内 COM4 后被其它进程（疑似 WorkBuddy/node 运行时）独占，无法在最后做实时端到端

  固件在真实硬件 67/67、门控逻辑单测全绿。给用户的演示命令：

### 结论
下位机已适配新 ACK 契约（每条指令恒有 OK/ERR 应答；异步事件 `# ` 前缀），web 侧配套以“非 `# ` 行=应答”
判定，二者联调协议一致；固件已烧录真实 Uno 并通过 67/67 验证。

## 补丁：Windows 读超时导致串口反复断连（回归修复）

续上一节“继续”。复查 `internal/serial` 发现此前为修“非阻塞读漏数据”而把
`commTimeouts.readTotalTimeoutConstant` 设为 200ms，但 `readLoop` 把**任何非 EOF 错误**当致命
错误 → `broken <- err` → 连接每 200ms（空闲即触发）被撕裂重连。后果：连接状态抖动、指令时有时无、
ACK 门控在超时窗口内接不到应答而误判通讯失败。这是我自己引入的回归，与 web 按键（用户自理）无关，但
会放大“指令发不出”的观感。

### 改动
- `internal/serial/windows_serial.go`：定义 `errTimeout`（`Timeout()=true` 的哨兵）+ `winERROR_TIMEOUT=1460`；
  `Read` 在 `ERROR_TIMEOUT` 时返回 `errTimeout`（非致命），其余错误照旧返回。
- `internal/serial/serial.go` `readLoop`：`err != io.EOF` 分支里新增 `if ne,ok:=err.(Timeout interface); ok&&ne.Timeout() { continue }`，
  读超时仅继续等待、不 `broken`、不断连。（Unix 侧 VMIN=0 超时 Read 返回 (0,nil)，本就 continue，无影响。）
- 新增单测 `TestReadTimeoutDoesNotBreakConnection`：用 `timeoutFakeSerial`（无数据返回 Timeout 错误）复现
