## 1. 为什么必须用有向包围盒（OBB），而不是 AABB

`core/tools/step_report.py` 输出的是 **AABB**（轴对齐包围盒）—— 即"件在世界轴上的投影范围"，
**不是件的自身尺寸**。一块相对世界轴转了 42° 的板，AABB 会比它自身大出近一倍。

实例（CAD 件 `17`）：

| 口径 | 三边 |
|---|---|
| AABB（`step_report.py`） | `[40.29, 71.358, 44.229]` |
| **OBB（`step_obb.py`）** | `[3.0, 8.0, **88.0**]` |

AABB 把一块 **3×8×88** 的窄条报成了 **40×71×44** —— 误差 5 倍以上，且**形状完全失真**。
所以任何基于 AABB 的尺寸推断都是无效的；Phase 1 起始阶段据此得出的结论已全部作废。

> ⚠️ 教训（与 `docs/STEP_KINEMATICS_VALIDATION.md` §1 同源）：
> **用错口径的测量工具，会把"工具的局限"表现成"数据的性质"。**

## 3. ⚠️ 装配基准（"地面在哪"）**无法**从 STEP 得出

要把 CAD 的板件搬到模型坐标系，需要一个**刚体变换**。CAD 与本模型**同向**
（两项独立证据：底座舵机轴 `[0,0,1]` → `base.axis`；肩/肘轴 `[0,±1,0]` → `shoulder.axis`），
所以只需一个平移。但**这个平移量无法自证**：

- STEP 里**没有"地面"这一语义** —— 它只有实体，没有"哪一层是台面"。
- 尝试用结构自洽锚点反推，全部得到**自相矛盾**的结果：

| 尝试的锚点 | 推出的 `z0` | 矛盾 |
|---|---|---|
| 底座舵机轴 `z=53.1` ↔ 模型 `19.5` | 33.6 | 肩轴推算高度 122.4 ≠ `column_link.length` 60 |
| 件 `1` 底面 `z=55.13` | 55.13 | 件 `7`/`11`/`8`/`14` 落到 **z ≈ −19.5**（穿地） |
| 整机最低面 `z=45.73` | 45.73 | 同上，且 `pieds` 实为**板间隔柱**而非脚垫 |

> `pieds sous la platine`（法语"板下的脚"）在本装配里**不是整机脚垫**：
> 它们成对出现在 `z≈65` 与 `z≈190` 两个高度、`x = +20.57 / −50.14` 左右对称，
> 夹住的正是件 `1` 的上下两端 —— 作用是把两块板**隔开**，是间隔柱。

**结论**：模型原点（底盘板底面 = 0）是**人为定义**的，CAD 无从给出对应关系。
因此本轮**只改 `size`（旋转无关量，可信），不改 `position`（需要基准，不可信）**。

> 若要进一步对齐位置，需要一次**带标尺的正交实拍**（与 `docs/hardware-measurement.md`
> 的既有方法一致），或由用户直接指定"CAD 的哪一平面 = 模型的 z=0"。

## 4.2 零件 → link 归属：几何判据（不是外观猜测）

判据链（脚本 `.workbuddy/analysis/map_parts_to_links.py`）：

1. **关节轴**取 4 个 SG90 输出轴（R = 6.20 mm，`docs/STEP_KINEMATICS_VALIDATION.md` §3）；
   底座两条共轴竖轴取中位代表 `base` 轴。
2. 对每个件算「到该轴的垂直距离 `perp`」与「沿该轴的投影 `t`」。
3. `perp` 小 ⇒ 该件是**这个关节附近的构件**；`t` 的正负给出**侧别**（上盖 / 底板）。

### 结论 A：底盘是「一件上盖 + 一件底板」

| 件 | 尺寸 | 法向 | 相对底座舵机输出轴的 `perp` / `t` | 判定 |
|---|---|---|---|---|
| `4` | 62.86 × 48.10 × 3.00 | Z | `perp` 17.5 / **t = +6.90**（上方） | **上盖板** |
| `12` | 69.04 × 58.64 × 3.00 | Z | `perp` 12.3 / **t = −17.45**（下方） | **底板** |

⇒ `robot.yaml` 的 `base_link.geometry` 只用了件 `4`。件 `12` 是**第二层底托**，
模型里没有对应几何（不影响轮廓与比例，**本轮不补**）。

### 结论 B：`column` 在 CAD 里是**一块竖板**，模型把它拆成了「转盘 + 两片侧板」

件 `1` 实测 **145.04 × 90.78 × 3.00、法向沿 Y** —— 是一块**竖直大板**，
跨越 z = 55.13 → 200.17（即「底座上表面 → 肩轴」的整段），**与肩轴的 `perp` 仅 28.33 mm**。
而模型把它表达为：转盘（件 `2`，58×58×3）+ 两片立柱侧板（件 `7`/`11`，52×21.6×3）。

件 `2`（58×58×3，法向 Y）与条 `1` **严格平行**、与肩轴 `perp = 0.91 mm`（**几乎穿轴**），
件 `3`（31.4×24.8×3）同族。

> ⚠️ 这是 CAD 与模型之间的**表达差异，不是缺陷**。用户已明确「**保持现有分件，只改尺寸**」
> ⇒ 此处**不做任何拆合**，仅记录该差异，以免后续读者把"模型比 CAD 少一块板"当成 bug。

### 结论 C：臂板族有一个**统一朝向的倾斜装配面**（不是「OBB 不稳定」）

§4「未改动」里写 `upper_arm`/`forearm` 的理由是「OBB 轴定向不稳定」。**该判断需要修正**：

件 `17`×3、`31`、`13`、`16`、`10`、`9`、`6`、`19`、`23`、`22` 的**薄维法向全部是
`[0.743, 0, 0.67]`**（与 +Z 成 **47.96°**，**不是 45°**），一致性极高。

⇒ 真正不稳定的**只是「哪个轴是最短维」的排序**（当两条较长的边数值接近时），
**法向本身高度一致**。这意味着臂板族**可以**被一次性组织起来 ——
`upper_arm`/`forearm` 的尺寸仍是可闭合项，只是需要先用这个共同法向建立**臂平面局部坐标系**
（沿法向 stack、在平面内取 (u, v)），再读长边与短边。

**为什么不现在就做**：这两块板挂着照片纹理，而纹理的**长宽比契约**是从 `size` 派生的
（`make_texture.py` 的 `load_plate_sizes` → `big_face_mm`）。改 `size` 会直接拉伸已拍好的
贴图 ⇒ 属于「看起来对、贴图反而坏掉」的改动，须与纹理轨一起决策。

## 5. 下游同步：新尺寸流到了哪里（这是本轮最容易漏的一环）

改 `robot.yaml` 的 `geometry.size` **不是**"改一个显示字段"那么简单 ——
它同时是几条**派生链**的输入。逐条审计如下：

| 下游 | 是否消费 `geometry.size` | 处置 |
|---|---|---|
| 前端 3D（`loadRobotModel.ts` → `Link.ts`） | ✅ 直接读 | 自动生效 |
| **MJCF**（`simulation/mujoco/mearm.xml`） | ✅ 视觉 geom 由生成器直出 | **重跑 `gen_model.py`** |
| **URDF**（`robot-package/mearm-v1/urdf/mearm-v1.urdf`） | ✅ 视觉 geom + 惯量 | **重跑 `gen_urdf.py`** |
| **`physics.yaml` 的 `[估算]` 质量** | ✅ 表头明写"由 geometry.size × 密度推算" | **按同一条规则重算**（见下） |
| MJCF / URDF 的**惯量** | ✅ 读 `physics.yaml` | 随上面两项一起重生成 |
| 纹理长宽比契约（`make_texture.py`） | ✅ `big_face_mm()` | **未受影响** —— 挂纹理的只有 `upper_arm`/`forearm`，两者本轮未改 |
| 运动学（`length` / 限位 / 标定） | ❌ 冻结白名单已排除 `geometry`/`details` | 零影响（黄金数据逐位一致，已验） |

### ★ 本轮真实踩到的坑：URDF 被漏掉了，而**没有任何测试会告诉你**

MJCF 有一条"产物必须与现算结果逐字节相同"的守卫
（`tests/sim/test_simulation.py::test_generated_mjcf_is_in_sync_with_config`），
**URDF 没有** —— 于是只重跑了 MJCF，URDF 里仍然是 `box size="0.094 0.082 0.007"`，
而 `pytest -q` **依然 196 passed**。

> 这与 `docs/STEP_KINEMATICS_VALIDATION.md` §1 是同一种失败：
> **"测出来了"和"有判据能测出来"是两件事。** 一条守卫只覆盖它认识的那条链。

**修法**：把守卫改成对**清单里声明的每一条生成链**都成立
（`core/tests/test_package_contract.py::test_generated_artifacts_are_in_sync_with_their_generator`，
参数化自 `GENERATED_CHAINS`）。新增生成链时只需加一行登记。
两条分支都**已证能红**（用 HEAD 版覆盖产物 → 报红并打印修复命令 → 重生成 → 转绿）。

### `physics.yaml` 质量项的重算（只动"板"那一项）

规则仍是该文件自述的「`geometry` 体积 × 材料密度」，且**只动板项** ——
螺栓与舵机的声明没变，按定义不该动（也不需要凭空发明螺栓密度）：

```
base_link:   m = 0.0800 − V(94×82×7)·ρ      + V(62.86×48.1×3)·ρ      = 0.0266
column_link: m = 0.0560 − V(66×60×7)·ρ − V(30×6×22)×2·ρ
                      + V(58×58×3)·ρ + V(52×21.6×3)×2·ρ            = 0.0336
（ρ = 亚克力 1190 kg/m³；复现脚本 `.workbuddy/analysis/recompute_derived_mass.py`）
```

模型总质量 **0.2173 → 0.1415 kg**。

> ⚠️ `base_link` 的该值**已知偏低**：CAD 里底盘另有一块底板（件 `12`）与 4 个间隔柱，
> 不在 `robot.yaml` 的声明里（用户明确要求不补进 `details`）⇒ 不计入。
> 要按 CAD 整机口径重算，这是唯一需要改的地方。

### ★ 这是"动物理"，所以做了**对照实验**而不是断言

`inertia` / `contact` 都在冻结白名单里（`PHYSICS_SECTIONS`）⇒ 改它**必然**让
`test_baseline_frozen.py` 报红，必须 `--update` 重新冻结。为了证明"这不是在动动力学"，
在改动前后各跑了一遍同一套测量（`.workbuddy/captures/sim2sim_{before,after}.json`）：

| 量 | 改前 | 改后 |
|---|---|---|
| sim2sim 报告**逐字段**比对 | — | **差异条数 = 0**（40 FK + 28 IK 用例全等） |
| 黄金数据 `--check` | — | **逐位一致** |
| HOME 稳态关节角 | `sh 1.137358 / el 113.187088` | **逐位相同** |
| HOME TCP | `[115.125857, 0, 108.464059]` | **逐位相同** |
| `gravity_torque` | `[-0, -0.03204831, -0.03107004, 2.3e-07]` | **逐位相同** |
| `constraint_torque` | `[-0, -0.00676259, -0.00642449, 0]` | **逐位相同** |
| 总质量 | 0.2173 kg | **0.1415 kg**（唯一变化） |

**为什么理论上必然如此**（与实测互为印证）：`base_link` 是**无关节的静态体**，
其质量与惯量不参与任何运动；`column_link` 的 COM 在 `[0,0,0.030]`，正落在
`base` 轴上 ⇒ 绕 Z 的重力矩恒为 0。所以本次改的是**账面一致性**，不是动力学。

### Sim2Real 预留接口的实跑证据

`simulation/README.md` §7 声明了 `Observation/Action/Reset/Step/State`。那四个方法读
**同一份 MjModel**，所以"参数同步过去了没有"是可以量的：
`.workbuddy/analysis/sim2real_probe.py` 在 MjModel 上直接读回 ——

```
① 几何  16/16 PASS  每个 visual geom 的尺寸 == robot.yaml 现在声明的 size
                     （含 base_link 62.86×48.1×3、转盘 58×58×3、侧板 52×21.6×3）
② 物理   6/6  PASS  每个 body_mass == physics.yaml 现在声明的 mass（含 0.0266 / 0.0336）
③ 闭环   4/4  PASS  Observation→Action→Step→Observation→Reset 全程可用
结果：23 PASS / 0 FAIL
```
