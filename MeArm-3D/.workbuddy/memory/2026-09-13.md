## 11. ⚠️ 工具层教训：同一文件的并发 `Edit` 会**静默丢更新**

收尾时生成了界面截图，发现**页头仍显示 `Phase 1–7`** —— 而我明明改过它。排查后确认：

**把针对同一个文件的 2 处以上编辑放进同一条消息（并行 tool call）时，每次 Edit 各自"读→改→写"，
后写者整体覆盖先写者的结果，而两次调用都报 success。**

本轮实测两例（都在本轮内部就已埋下）：

| # | 丢失的编辑 | 被谁覆盖 | 症状 |
|---|-----------|---------|------|
| 1 | `robotStore.ts` 新增 `teachTrack` / `teachRecording` **初始状态** | 同批的 action 实现编辑 | `tsc -b` 报 `missing the following properties from type 'RobotStore': teachTrack, teachRecording`（幸好 tsc 抓到了） |
| 2 | `App.tsx` 的 `Phase 1–7` → `Phase 1–13` | 同批的 `<TeachPanel />` 挂载编辑 | **完全静默** —— tsc / vitest / build / e2e 全绿，只有截图看得出来 |
| 3 | `TeachPanel.tsx` 的 notes 文案清理 | 同批的 import 清理编辑 | 静默（残留 `` {`${50}ms`} `` 这种怪写法） |

**判据（改完立刻查）**：并行改同一文件后，`grep` **逐个**确认目标字符串都变了。
`tsc -b` 能抓出"接口声明了但初始值没加"这一类；**但纯文案/JSX 的丢失只有截图或 DOM 断言能发现**。

**修法（已写进 `~/.workbuddy/MEMORY.md`）**：**一个文件一次 Edit，串行提交**；
只有**不同文件**的编辑才可以并行。本项目后续所有编辑按此执行。

> 顺带：截图脚本传 POSIX 风格路径给 Windows 上的 Node 会落到 `<当前盘>:\e\cnb\...`
> （`/e/cnb/...` 被当成"当前盘根下的 e/cnb"），必须传 `E:/cnb/...` 或反斜杠路径。

## 3. ★ 本轮最有价值的结论（都已写成测试）

### 3.1 IK 验收必须加载**真实 `ik.ts`**

用 Python 重写一份 IK 只能证明"我又写了一遍、而且自洽"，证明不了 `ik.ts` 是对的 ——
而 `ik.ts` 才是真正驱动机械臂的那一份，它的错**不会**被前端自己的 FK 测试发现
（两者共享同一套旋转约定，会一起错）。

判据结构设计成**被测对象只剩一个**：
目标点由 MuJoCo FK 生成 → 被测的是真实 `ik.ts` → 用 MuJoCo FK 评判。
实测 120 随机 + 256 限位角点：**376/376 成功**，`max = 1.137e-13 mm`。
顺带把**前端 `fk.ts` 与 MuJoCo** 也对撞（同 376 点，`max = 1.137e-13 mm`）。

桥必须用 **Vite 的 `ssrLoadModule`**：`loadRobotModel.ts` 里有 `@config/robot.yaml?raw`
（Vite 专属语法），且所有内部导入都是**无扩展名**的，Node 两条都不认。
桥用 `--in/--out` 文件传 JSON 而不是 stdout —— Vite 会往 stdout 打日志。

### 3.2 两条机构学结论（算术 + 实测双重钉住）

| 结论 | 依据 |
|------|------|
| **`elbow-down` 支恒不可行** | `θe = θs + α`，而 `elbow.limit_min (108.44°) > shoulder.limit_max (49.45°)` ⇒ α 恒 > 58.99° > 0。⇒ 本机**只有 elbow-up 一支存在** |
| **可达工作空间的内锥是空的** | `dr = l1·sinθs + l2·sinθe` 对 θs 递增、对 θe 递减 ⇒ 最小在角点 `(θs_min, θe_max)` = **65.62 mm > 0**。⇒ 真机**够不到自己的中轴线**（"离底盘越近越容易够到"是错的）；`ik.ts` 里「方位角不定」那段分支在本机**不可达**，不能当成已覆盖路径 |

### 3.3 MuJoCo 三个工具层事实

1. **运行时改 `model.geom_pos`/`geom_size` 完全无效** —— `mj_forward` 不重算静态 geom 的
   `geom_xpos` 与 broadphase AABB。实测把工作台 z 从 15mm 抬到 100mm，臂的稳态位置与接触对
   **一字不变**。⇒ 变体场景必须用 `mujoco.MjSpec` 在**加载期**改 XML（`MeArmSim(xml_text=...)`）。
   **但 `geom_contype/conaffinity` 运行时改是有效的**（走逐对掩码，不走 AABB 缓存）。
2. **`dist > 0` 的软接触仍会施力** —— 下压位形 `dist=+1.44mm`，但
   `qfrc_constraint=[0,−0.23325,−0.145184,0]`、执行器满力矩 0.1765、
   禁用台面后 TCP 掉 28.26mm。⇒ **"接触表里有记录"和 `dist` 都不是证据**。
3. **固定关节在 MJCF 里没有 `<joint>`** ⇒ `mj_name2id(mjOBJ_JOINT,"tool")` 返回 −1；
   它的坐标系原点 = 子连杆 body 的 `xpos`（同一个量）。

### 3.4 三个「只在特定调用方式下暴露」的静默 bug（D54）

| bug | 症状 |
|-----|------|
| 控制周期累加器写成**局部变量** | `step(1)` 连续调用永远到不了 10ms 阈值 ⇒ ctrl 永不更新、**命令完全不生效**；而 `step(200)` 一切正常 ⇒ "用 settle 测全挂、用 step(200) 测全过" |
| `settle()` 用**单步**速度判静止 | `reset()` 后 qvel 恒 0 ⇒ 第一次 step 就返回 ⇒ 所有测试读到**从未移动过**的位形 |
| 惯量**双重单位换算** | `physics.yaml` 已是 SI，生成器又 `mm2m()` 一次 ⇒ 惯量 1e-11，`%.6f` 后**显示成 "0"** |

## 7. 真值冻结（用户要求「保存目前的运动学物理数据不变」）

**交付**：`tools/freeze_baseline.py` · `config/baseline-kinematics-physics.json` ·
`tests/sim/test_baseline_frozen.py`（11 项）· ADR **D55** · README §11。

**★ 核心设计：两级判据，不用整文件哈希。**
`robot.yaml` 同时装**运动学**（links.length / joints / actuators / tcp / homePose）与
**外观几何**（links[].geometry / details）—— 而文件里早写着「改 geometry 只影响外观」。
后续"图像采集 → 更真实建模"**必然要动外观**，整文件哈希会把合法变更判成违规
⇒ 守卫被绕过 = 没守卫。所以：
- L1 整文件 sha256（记录用）
- **L2 语义核心 sha256（真判据）**：字段**白名单**（不是黑名单）——
  将来新增运动学字段忘了登记会**漏检**而非**误报**；误报会让人把守卫关掉。
- `recording` / `deterministic.seed` 不算物理量（改记录开关不该报"物理被改"）。

**对照实验（辨识力，5/5 通过）**：改 `geometry.color`/`size`/`details` → 放行；
改 `length` / `parent` / `joint.limit` / `coupling.gain` / 标定 offset →
报错；改 `gravity`/`friction`/`timestep` → 报错；改 `recording`/`seed` → 放行。
**反向验证**（临时把 `column_link.length` 60→61）：测试**确实失败**且报错精确到
`kinematic_summary/links/column_link: {'length': (60, 61)}`；还原后**字节一致**、11 passed。
> 一条永远返回通过的守卫，和没有守卫在报告里长得一模一样（都是绿色）—— 所以
> 「守卫有辨识力」必须单独测。变异全部在**内存**做（deepcopy + 改 dict），不碰 yaml，
> 避免"测试跑挂就把真值改坏"的尾部风险。

**修掉的 bug**：`_diff_summary` 把列表元素一律当 dict 迭代 ⇒ 遇到 `gravity: [0,0,-9.81]`
这种**标量列表**直接 `TypeError: 'float' object is not iterable`。
（只有真的去改 gravity 才会触发 —— 又一个"测试全绿但路径没走过"的例子。）

**★ 两条决定性实测事实**（都不是推断）：

1. **plate 的大面法向 = `size` 里最小那一维。**
   `[22,5,74]` → 大面 22×74、法向 **±Y（左右）**；`[94,82,7]` → 法向 ±Z（水平）。
   ⇒ 相机摆在机械臂**正前方**只能拍到大臂/小臂板的 **5mm 窄边**，
   **必须转 base 关节 90° 或绕到侧面拍**。这正好用上了用户说的"可以让我变更方向"。
2. **`RoundedBoxGeometry` 的 UV 是"每面各自铺满 [0,1]"、与长宽比无关。**
   直接挂一张图 ⇒ 6 个面各显示一遍同一张图且被非等比拉伸。
   ⇒ 必须**按面用材质数组**。实测 6 个 group **覆盖全部 900 顶点**，
   `materialIndex → 面`：`0=+X 1=-X 2=+Y 3=-Y 4=+Z 5=-Z`（与 BoxGeometry 官方顺序一致）。

**★★ ADR D56：PIL 的 `Image.transform(QUAD)` 会引入 +12~17px 的静默平移。**
排查路径（每步排掉一个假设）：四角估计 max|Δ|=1.00px ⇒ 排除；四象限着色验证角点顺序
完全一致 ⇒ 排除；刻度间距比 1.0027 ⇒ 排除缩放。**换自实现 homography 重采样后精确命中**
（真值 [185,370,554]，PIL QUAD → [197,387,567]，自实现 → [185,370,554]）。
⇒ `rectify()` 改为自实现 `homography + _warp + _sample_bilinear`。
**教训**：它不抛异常、尺寸正确、内容大致对，只"挪了一点点" ⇒ 归因方向全错
（与 D51 接触记录≠接触力、D54 只在特定调用方式暴露的静默错误同族）。
已加**防倒退测试**：扫描 `rectify` 源码禁止 `Transform.QUAD` 复活。

**附带修掉**：`_sample_bilinear` 的区域判据用严格 `u∈[0,w-1]` ⇒ homography 浮点误差
（反投影出 `99.9999998`）把边界行判成区域外填背景色 ⇒ **纹理边缘一圈白边**。
真实照片四角估计永远差半像素 ⇒ 生产必然发生。改半像素容差 `u∈[-0.5, w-0.5]`（边缘 clamp）。

**命名一致性地雷（自查发现）**：脚本原本生成 `upper_arm_link_detail3`，而指南写的是
`upper_arm_brace` ⇒ 用户按指南命名、脚本找不到，**且不报错**。已加 `DETAIL_ALIASES`
把命名对齐，并加测试双向比对"指南提到的名字 ↔ 脚本认识的名字"（含序号后缀剥离）。

   真相：横向后**能再靠近** 1.78 倍，所以 px/mm 的**上限** ×1.78。

## §11 真机摆位轨：用户拍板「使用真实机械臂」（ADR D58）

> ⚠️ **本节推翻 §10 的两条结论**：① 「隔离必须靠白卡」→ 不成立；
> ② 「转 base ±90° / 靠近 1.78 倍」→ base 限位只有 ±60°，且转向对分辨率**零和**。
> 下面全部是**实测**数据，不是推导。

### 真机链路（本轮打通）
- 后端：`backend/bin/armpilot-backend.exe -c config.serial.yaml`
- 串口：**COM16 · USB-SERIAL CH340 · 115200 8N1**（系统内唯一串口）
- 启动打印：`[serial] 已连接 COM16` · `设备: STATUS S6=90(H) S7=90(H) S8=90(H) S9=90(H)`
  ⇒ 四舵机全 90° = 固件开机位 = HOME，**与 `robot.yaml` 的 `homePose` 语义一致**
- 枚举端口用 `pyserial.tools.list_ports`（`win32com` 拿不到、`reg.exe` 被安全策略拉黑）

### 新工具 `tools/set_joints.mjs`（真机"只动一个关节看一眼"的入口）
既有 `verify_pose.py` / `verify_serial_e2e.mjs` 是**验收**用途，不能当调试摇杆用，故单开。
五条安全设计（都在文件头注释里）：
1. **限位来自 `hello`，不硬编码**；发送前本地校验，越限直接拒绝并打印范围。
2. **只有 `device === 'serial'` 才允许发送**。
   ← 因为实测 `hello` 里**没有 `connected` 字段**（`protocol/serial-v1.md` §5.1 写了，属**文档漂移**）。
3. **"保持不变"的关节必须取最新 `joint_state`，不能取 `homePose`**。
   ← `hello` 与 `joint_state` 同时到达且 **`hello` 在前**；若在 `hello` 分支就发指令，
   未指定的关节会 fallback 到 `homePose` ⇒ 那不是"保持"，是**把臂拉回 home**。发送点必须挪到收齐 `joint_state` 之后。
4. `--home` 是为**实验可比性**加的：`--settle` 的"保持不变"语义会让状态**跨实验累积**。
   实测先 `base=-20` 再只发 `shoulder=30`，后者把 base 保持在 −20 ⇒ 两组对比图机位不同，读数全废。
5. 真机**无位置反馈**：`--settle` 只是"给舵机时间走完"，**不是"已确认到位"**。

### ★ 三条实测结论（本轮的核心产出）

**A. `base` 旋转对分辨率是零和的 —— 转 base 是纯亏。**
远端确实放大 ×1.08（base 0→−20°），但板法向偏 20°、投影缩短 `cos20° = 0.94`
⇒ **净 1.015**，还白搭一层透视。

**B. 肩/肘摆动改变不了 `px/mm`。**
相机在正前方（−Y），摆动平面（X–Z）**平行于像平面** ⇒ 摆动既不改变距离、也不改变投影长度，
只改变板**在画面内的朝向**。三证：
① 仿真扫 shoulder，大臂板倾角 **89.2°→79.2°→59.2°→41°**（板随肩同步转，**长度不变**）；
② 真机 HOME vs `shoulder=30` 两帧**暗色投影面积 236345 → 230804（−2.3%**，差值来自遮挡）；
③ base 旋转净 1.015。
⇒ **提高 `px/mm` 只能物理靠近相机，没有任何软件办法。** 相机上限 1280×720，
当前 `s ≈ 3.80 px/mm`（74mm 大臂板 → 281px），目标 ≥6 需物理靠近约 **1.6×**。

**C. 「白卡隔离出单块板」不成立。**
实测暗像素占整帧 **25.7%**（左下象限 **65%**）；板、立柱、底座、舵机、控制板**全是同一种黑**，
且板与板**由螺栓物理相连** ⇒ **不存在"只含一块板"的连通域**，
最大暗色连通域必然是**整条臂 + 底座**（实测占 97.7%，bbox `x[0,1040] y[0,690]`）。
**白卡挡得住背景，挡不住结构性连通。**

### 替代方案 `tools/project_plates.py`（相机标定 + 运动学投影）
三块目标板大面法向实测均为 `(0,1,0)` ⇒ 板面**平行于像平面** ⇒ **正交模型就够**：
`u = ox + s·X(mm)`、`v = oy − s·Z(mm)`（画面右 = 世界 +X，画面上 = 世界 +Z）。

目标函数**三项相乘**：① 框内暗色比例 · ② 板间空隙亮色比例 · ③ 框边命中「暗↔亮」边界比例
```python
inside * gap_bright * (edge_hit / 1.5 + 0.05)
```
**②空隙项是防退化的关键**：实测只优化①时，`s=2.5` 会把三块板挤成一团塞进左下底座暗区，
拿到 **97.4% 的假性满分**（而 `oy=770` 已在画面外）——与 D56「静默错法」同族。
另加"空隙 <30px 直接判 0" + 收窄 `s ∈ [3.8, 5.6]`。

标定结果 `CALIB = {s: 3.80, ox: 530.0, oy: 645.0}` **数值自洽**（三块板投影与图像位置一一对应），
**但精度不足**：框边缘会夹进橙色线缆/背景。
又：我"人工把 ox 从 530 改成 460"的修正**是错的**，A/B 对比证明 **ox=530 才对**（数据也一致：框内暗色 69.8% vs 41.5%）。
⇒ **一律要目视复核叠加图 + 纹理；数据会骗人。**

## §12 走 A 方案（物理靠近）时捅出来的四个更深问题（ADR D59）

用户拍板 **A：把机械臂挪近相机**。为把"挪一点→量一次"压成一条命令，
给 `tools/project_plates.py` 加了 `--capture`（开摄像头抓帧）+ 一句话 `CONCLUSION`
（报 `s`／大臂板 px／边缘过渡 `ramp`／投影是否出画）+ **搜索边界命中检测**。
**第一次跑就推翻了 D58 里当成真值的 `s = 3.80`。**

### ① ★ 旧标定 `s = 3.80` 是**搜索下界被截断**的值，不是测量结果

`s = 3.80` **恰好等于当时的 `S_LO = 3.8`** ⇒ 被区间截断，不是自由极值。
放宽到 `CALIB.s × 0.6~1.8 = 2.28~6.84` 后最优落到 **`s = 2.58`**。
⇒ 同一台机器、同一场景，"测量值"从 3.8 变 2.58 —— **这就是三块纹理全不合格的根因**。
**已加永久防护**：最优落在端点 2% 内就打印 `⚠️ s 落在搜索边界上 ⇒ 用 --s-range 放宽重跑`。

> **可复用铁律**：**任何带区间的搜索都必须显式检测"最优解是否贴边"。**
> 贴边 = 该值不是测量结果、是区间的人为截断。**比"分数不高"隐蔽得多** ——
> 分数看着还行、数值看着合理，实际毫无意义。

### ② 放宽区间后投影**依然对不上**

新最优 `s=2.58 / ox=660 / oy=445`，score 仅 **18.2**，叠加图**三个框都没贴板边**。
手动拨回旧标定附近（`s 3.4~5.0`、`ox=560`、`oy 600~690`）逐点扫，score 只有 **1.9~4.2**
（比 18.2 还差 4~9 倍）。⇒ **"缩放+平移"模型在本场景无法定位**：
- 板/立柱/底座/肩座**同一种黑且物理相连**，框落哪都在暗区；
- 三块板在 HOME 位**竖直首尾相接**（立柱 Z[38,60] 紧接大臂 Z[59.8,134.2]）⇒ **没有一条边能唯一定位**；
- **相机相对臂的真实位姿从未标定**，3 个自由度只有"三项乘积"一个标量约束。

### ③ 新发现：机械臂被画面**顶边裁掉**

行剖面：`y=0` 处有一条 **x[506,760] 连续暗带**，y=2 起才裂成多段 ⇒ 顶边切断。
**目标板不在画面内，四角必然缺角** ⇒ 无论 A 还是 B，**重新取景都是先决条件**。

### ④ ★ 改用「致动并观察」（motion-diff）—— 纯几何走不通时的通用突围手段

动一个关节 → 拍前后两帧 → 差分 ⇒ **差分区域 = 该关节及其下游零件**。
完全不依赖"相机在 −Y""板面平行于像平面"等任何假设。

| 动作 | 变化像素 | 占比 |
|---|---|---|
| shoulder 0.85→45 | 183097 | **19.87%** |
| elbow 112.62→141.8 | 131320 | **14.25%** |
| base 0→60 | 148177 | **16.08%** |

- ★ **物理臂确实在跟命令走** ⇒ 排除掉电/堵转/打滑。
  「MG90S 无位置回读」只是说**不能证明"到位"**，**不等于"没动"** —— 现在有正面证据了。
- 「随 shoulder 变 **且** 不随 elbow 变」筛出的区域 = **大臂板**
  （实测 x≈622–706、宽 84px）—— **这是纯几何做不到的归属判定**。
- ⚠️ 但**给不出干净单板四角**：肩座/平行杆/线缆/阴影连成一片，
  PCA 外接四边形出来的是整块区域（bbox 395×445）。
  ⇒ 适合**归属判定 + 粗定位**，精确四角仍需人工标 + 目视复核。

`joint_probe.py`（motion-diff 全流程）、`_grid.jpg` / `_zoom_home3x.jpg` / `_az_compare.png` /

### ★ 本轮方法论（跨项目可复用）
1. **区间搜索必查贴边**（① 的教训）。
2. **"测量值"与"边界截断值"长得一样**：发现两个相互矛盾的读数时，
   先查是不是区间设窄了，别急着调模型。
3. **纯几何推理走到尽头时，用"致动并观察"建立对应关系** —— 让系统自己动，
   差分就是最可靠的"哪个像素属于哪个部件"的答案。
4. **"无反馈"≠"没动作"**：没有位置回读不代表不能证明它动了，差分就是证据。

## §13 新机位后：窄带 PCA 定出四角，纹理首次落地（ADR D60）

用户按 D59 要求**重新取景并挪近** ⇒ 新机位里**整臂完整入画**（不再被顶边裁掉）、背景干净。

### ① 先纠一个误报：`ramp=10.78px 失焦` 是**假的**
`ramp` 是在**投影框边缘**测"暗↔亮"过渡的；旧标定定位本身就错（D59），框落在**暗区内部**
⇒ 边缘压根没有真实边界 ⇒ ramp 被拉长到 10px。放大目视：板边缘过渡约 **2px，并未失焦**。
⇒ **`ramp` 只有在四角正确时才有意义**，绝不能拿它反推"相机失焦 / 别再靠近"。

### ② 整臂剪影 IoU 配准（`fit_arm.py`）—— 失败，但失败得有信息量
用已知模型 + B 位姿态（`shoulder=45`）投影**整条臂剪影**，与实际剪影做 IoU：

| 版本 | 做法 | IoU | 结果 |
|---|---|---|---|
| v1 | (s, ox, oy) 全自由 | 36.3% | 最优解把模型推到 **`oy=830`（画面外）** —— 又是 D58 退化模式 |
| v2 | **bbox 中心强制对齐**，只搜 s | **25.3%** | s=3.50 / ox=540 / **oy=644**（与内置 CALIB 3.80/530/645 接近 ⇒ 交叉印证）|
| v3 | 再联合搜 (s, shoulder, elbow) | **30.2%** | s=4.35 / shoulder=41.5° / elbow=115.0° |

- **30.2% 是上限**：叠加图显示**模型的臂整体比实拍"高"** ⇒ 模型几何与 3D 打印实件存在
  **系统性差异**；同时反解出**物理臂实际角度与下发命令差 ~15°**（开环无回读的必然）。
- 踩坑：`table_top`（约 1m 见方）也在投影件里 ⇒ 剪影被撑成**全屏矩形**，
  IoU 退化成"实际面积占比"（19.3% ≈ 10069/57600）。**必须排除桌面。**

### ③ ★ 可用方案：窄带 PCA（`plates_corners.py`）
板本身是一条**直带** ⇒ 沿长轴开窄带（半宽 ~35px），**带内**暗像素 PCA 取主轴极值四角。
带外的一切（螺栓 / 立柱 / 平行杆 / 线缆）被**结构性排除** ——
这是绕开"整条臂是同一连通域"（D58 ③）的正解。
实测：大臂 **241×65px**（长宽比 3.69 / 真值 3.36）；小臂 **200×72px**（2.76 / 3.78）。
⚠️ 中心线端点仍是**目视读数**（±15px）⇒ 精度有限，但可复现、且比整图分割好得多。

### ④ 纹理首次落地（2 块；`make_texture.py --corners`，四角再向心收缩 8% 避边缘）
- `forearm_link` 18×68mm → 180×680px：✅ **干净可用**（黑底 + 两枚螺栓 + 镂空）
- `upper_arm_link` 22×74mm → 220×740px：⚠️ 中部**一条橙色线缆横穿**
⇒ **线缆无解**：实拍里线缆**悬在板前面**，只要框圈住板就必然含它；
向心收缩只能去**边缘**、去不掉**中间**。**软件层面没有办法。**
其余 7 块（`base_link`/`column_link`/`column_link_side`/`upper_arm_brace`/`forearm_brace`/
`tool_link`/`jaw_link`）在 B 位**被遮挡或不在视野**，需额外姿态/机位。

### ⑤ 环境事实
- MuJoCo 离屏渲染在本机**上限约 320×180**（640×360 会失败）。
- 渲染要看到颜色必须先 `m.geom_matid[i] = -1` 清材质，否则 `rgba` 被 material 覆盖成白。

### ★ 本轮方法论
1. **一个判据只有在其前提成立时才有意义**：`ramp` 依赖"框落在板边上"，框错了它就成了噪声
   —— 不要拿一个下游指标去反推上游前提。
2. **"模型对不上"要先怀疑模型，别一直调相机参数**：联合搜姿态后 IoU 只从 25%→30%，
   这就是"模型与实件有系统性差异"的证据。
3. **形状约束比位置约束强**：整臂轮廓 IoU ≫ 三个矩形框（后者欠定）。
4. **物理条件决定上限**：要拿到干净纹理，必须先满足
   "板完整入画 + 不被线缆横穿 + 目标面正对相机"，三条都是物理条件。
