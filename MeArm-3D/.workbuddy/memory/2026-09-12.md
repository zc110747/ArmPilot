## 23:35 · 修复「Real 模式但后端末端是 sim」——准入校验必须拒绝（ADR D43）

### 一、根因：`set({ mode })` 写在准入校验**之前**（D41 只修了一半）

用户报障：「前端显示 Real 模式后端末端是 sim，非真机」。澄清后确认用户**没加 `--real`**，
后端跑 `config.yaml`（`device: sim`）**完全正确** —— 错的是前端：

```ts
setMode(mode) {
  set({ mode });          // ← 无条件先写（D41 遗留）
  if (mode !== 'real') { …; return; }
  if (device !== null && device !== 'serial') {
    get().pushLog('err', `…末端是「${device}」而非 serial…`);
    return;               // ← 只 return，mode 已是 'real'
  }
}
```

⇒ 点 Real Robot 的**唯一效果**是按钮高亮切到 Real + 多一条 err 日志。UI 结论与事实相反。

**最坑的一点：旧测试把这个 bug 固化成了契约**（`mode-transport-link.test.ts`）：
`expect(useRobotStore.getState().mode).toBe('real');` + 注释"用户意图被记录"。
所以 D41 之后没人发现它还错着。**测试锁定错误行为，比没有测试更危险。**

### 二、修法（4 处）

| # | 位置 | 变化 |
|---|------|------|
| 1 | `robotStore.setMode` | 校验**全通过**才 `set({ mode:'real' })`；否则保持 simulation + pushLog 说明原因与修法 |
| 2 | `robotStore.setMode` | 新增 `device === null`（hello 未到）分支：**拒绝**。旧版在此乐观放行，正是 `--real` 自动切"假成功"的真凶 |
| 3 | `useAutoConnect` | 抽 `decideAutoRealSwitch()` 纯函数；订阅 **connection + transportStats 双变化**，等 device 到达再切 |
| 4 | `JointControl` | 两条 `mode==='real'` 但末端不对的提示 → "⚠ 状态异常（应由 setMode 拒绝）"，降为纵深防御 |

**关键决策（用户拍板）**：校验不过时**拒绝切换**，按钮保持 Simulation 高亮（所见即所是），
而非"切换 + 醒目警告"。代价是点按钮"没反应"，所以每条拒绝都要说清 why + how to fix。

**`device===null` 的取向在两种场景下必须相反**（易漏）：
- 安全门 `flush`（D41）→ **放行**（少拦一条命令 ≠ 危险）
- UI 切换 `setMode`（D43）→ **拒绝**（假"已切"会误导操作）

## 23:10 · 一键启动脚本 + 修复「启动后只动 sim 不动真机」（ADR D42）

### 一、根因：页面默认停在 MockTransport，且**全仓无自动连接**

用户报「一键启动后未操作真实设备，而是 sim 数据」。不是脚本问题——脚本把后端
（甚至 `-c config.serial.yaml`）都起好了。问题在网页侧：

- `ConnectionControl.tsx`: `useState<TransportChoice>('mock')` ← 默认 Mock
- `App` / `main.tsx` / `ConnectionControl` **都没有任何自动连接 `useEffect`**

⇒ 页面停在浏览器内仿真，拖滑杆只动虚拟臂，真机纹丝不动，而 UI 一切正常（静默失败，
与 D41 同类）。

### 二、修法：环境变量驱动，不污染手动开发

| 方案 | 否决理由 |
|------|---------|
| 前端默认改 websocket | `npm run dev` 手动调试被改；生产构建会连不存在的后端 |
| 页面永远自动连 WS | 同上，且局域网访问会意外连到别人后端 |
| **env 驱动（采纳）** | `start.bat` 注入 → 自动连；`npm run dev` 不注入 → 行为不变 |

新增：
- `frontend/src/hooks/useAutoConnect.ts` — `parseAutoConnectIntent()`（纯函数，12 项单测）
  + `useAutoConnect()`（两个 effect：① 发起连接 ② 连接成功后再按需切 Real Robot）
- `frontend/src/components/RobotControl/wsUrl.ts` — 从 ConnectionControl 抽出的
  `getDefaultWsUrl()`，供自动连接复用（按 `window.location.hostname` 推导，局域网正确）
- `frontend/src/vite-env.d.ts` — 补 `ImportMetaEnv` 类型声明
- `frontend/tests/unit/autoConnect.test.ts` — 12 项
- `start.bat` — 注入 `VITE_AUTO_CONNECT=ws`；`--real` 时另注 `VITE_AUTO_REAL=1`

**`VITE_WS_URL` 刻意不设**：让前端按来源主机推导，局域网设备才连得到正确后端（D40 原则）。

### 四、★ `start.bat` 的两个致命 .bat 陷阱（本次实测踩到）

1. **`if (...)` 块内的裸 `>` 是重定向，会掐死整个块**
   `echo  step1. Connection -> WebSocket` ⇒ cmd **解析期**就把它当重定向：
   该行丢失 + 块内后续跳过 + 报「此时不应有 to。」，
   且**生成名为 `WebSocket` / `inside` 的垃圾文件**（已误建并清理）。
   ⇒ 文本里的 `>` 一律写 `^>`；`(` `)` 写 `^(` `^)`。

2. **`start "标题" cmd /k "cd /d "X" && prog"` 引号嵌套是坏的**
   剥掉外层引号后首个 token 被当目录，然后执行名为 `then` 的命令
   （报「'then' 不是内部或外部命令」）。
   ⇒ 用 `start "标题" /d "目录" "程序" -c "参数"`，不自己拼 `cd &&`。

### 二、★ 根因：「`mode` 是死状态」——这是本次要修的真问题

用户报「real 真机执行时未运行」。**不是连接问题**，而是 `mode` 从未接入命令路径：

3. **UI 显式化**：`JointControl` 加 `mode-routing` 提示条（纯仿真 / 已拦截 / 正在驱动真机）。

**关键决策**：安全门**只拦真机链路** —— 不能简单"simulation 就不下发"，
那会打死 Phase 7/8 的 mock 与 device=sim 仿真闭环。
`device` 未知（未 hello）时按 **false** 处理：**宁可少拦，不要误判**（有专门单测锁定）。

### 关键设计点 / 本轮踩坑

- **拖动平面必须冻结**：每帧按当前 TCP 重建平面会形成自反馈环
  （目标变→关节变→TCP 变→平面跟着变），手感「飘走」且永不收敛。
- **越界不钳位**：球壳边界 `[40,200]` 与关节限位**不是同一个约束**，
  钳位会造出「看似合法、真机做不到」的姿态，且让工作空间边界从界面上消失。
- **锁死分量取精确相等**：`snapToMode` 显式设回锚点值，使 `target[2] === anchor[2]`
  成为可断言的**定义**，而非数值巧合。
- **滑杆 / HOME / ZERO 属「非目标驱动」** → 让 `target` 跟随新 TCP 并清空 `ikStatus`，
  否则幽灵标记停在旧位置误报「未到位」。
- **3D 拖动 e2e 必须走 CDP 真实鼠标事件**：`dispatchEvent` 造的 pointer 事件绕不过 R3F 射线拾取。

- **类型收窄**：测试里 `expect(result.success).toBe(false)` 不构成 TS 收窄，读 `result.reason` 报 TS2339；
  加 `if (result.success) throw new Error(...)` 兼作断言失败时的兜底报错。
- `model.joints` 含**固定关节**（`tool`），而 `commandJoints` 只含可动关节 →
  遍历限位断言必须用 `movableJoints()`，否则读到 `undefined`。

## ★ 本轮最值钱的发现：量化精度就是跟踪误差的下限
e2e 首跑 `Phase 8：跟踪误差统计归零（stat-lag）` **FAIL — 0.02°**。
根因不是机械臂没到位，而是**双方用不同精度表述同一个位置**：
前端内部 `elbow = 112.6185771989`，`JR` 线只保留 1 位小数 → `112.6`，
直接相减恒差 **0.0186°** ⇒ 面板永久显示 `0.02°`、「正在逼近目标」**永不熄灭**。
**这是个假误差**，而它同时出现在 StatusPanel（「滞后 X°」）与 ConnectionControl 两处，是用户可见的。

修法：在 `wsProtocol.ts` 显式声明链路精度并**只量化命令侧**（不量化测量的状态，否则会掩盖真实误差）：
```ts
export const WIRE_JOINT_STEP_DEG = 0.1;
out[id] = Math.round(v * 10) / 10;   // ⚠️ 不能写 Math.round(v / 0.1) * 0.1（0.1 不精确 ⇒ 差 1 ulp
                                     //    ⇒ "误差 0"退化成 1e-14 ⇒ moving 再次永真）
```
同时**更新了一条既有的、不再符合现实的单测**：它把 `jointsAt(30)`（全精度）当成后端回推值，
而后端**永远不可能**回推 112.6185771989 —— 真实回推值是线上值。改为 `onWire()` 包装。

## 其它四条语义（都写进测试）
- **`OK JR` 是目标角，不是实际位置**：只做标定核对（容差 0.1°，告警不阻断）。
  拿它发布状态 ⇒ 误差恒 0。单测有一条专守："ACK 到达**不发布**状态"。
- **ACK 门控 + latest-wins（不排队）**：在途期间新命令只覆盖待发槽。
- **间隔节流禁用 `time.Sleep`**：会卡住读循环（回执靠它消费）⇒ 自锁。
  首版就是踩了这个，表现为"发完第一条就再也收不到回执"。改为撤下在途 + 定时器补发。
- **重连补发当前命令，且只在重连时补**：首次无条件补发会白白占用一次节流窗口，
  打掉 Phase 7 锁定的时序契约（`transport-loop` 阶跃断言立刻失败）。
  e2e 验证方式最直接：杀掉后端 → 重启（新 sim 从 HOME 起步）→ Actual 必须回到 29.9°。

## 新增 `tools/verify_pose.py`（★ 核心，零新依赖：numpy + PIL）
- 期望值**唯一来源** `config/robot.yaml`：`joint = reverse ? (offset−servo)/scale : (servo−offset)/scale`；
  关节限位由**舵机硬限位经标定反算**，并与 `joints[].limit` 互校（实测完全一致）。
- **两个判据，两个都要过**：`--tol` 绝对误差（默认 5°，含公共偏置，只作粗筛）+
  `--dtol` **帧间差**（默认 1.5°，对参考帧取差抵消公共偏置，**锐利判据**）。
- 拟合**不喂答案**：种子只用 锚点角 + homePose + **按限位铺的 3×3 网格**（±12° 局部扰动），
  期望角**绝不入列**。取代价最小者定案并报告用的哪个起点。
- `--selftest`：合成掩膜验搜索器收敛性（断言「解代价 ≤ 真值代价」）+ 打印**轮廓厚度→偏置**表。
- `--overlay` 出叠加图（绿骨架 + 橙圈肩/肘/腕/TCP + ASCII 文字），`--json` 出逐帧结果。
  实测耗时：自检 29s；6 帧真照片 7.5s。
