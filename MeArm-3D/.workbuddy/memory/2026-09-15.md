### ★ 误判复盘：自研解析器的能力边界 ≠ 数据的缺陷（**这条要长期记住**）

我最初用自研正则解析器读这个文件，得出「110 个装配实例只指向 8 个无几何空容器、
50 个实体全挂在 46 个孤儿 PRODUCT_DEFINITION 上、**0/241** 可达几何」并写成
`BLOCKED` / `Level 0：输入不具备`。**该结论是错的。**

用户指出「不要自己写解析器，使用完整的开源项目，感觉是解析的有问题」——
**用户判断正确**。改用 **OCCT**（`cadquery-ocp`，`STEPCAFControl_Reader` +
`XCAFPrs_DocumentExplorer`）读同一份文件：

```
nodes=111  leaves=103  with_geometry=111  servos=4       ← 111/111 全部有几何
```

自研解析器静默丢弃的**三处**机制（都很隐蔽，修完一处还会被下一处继续骗）：
1. **复合实例语法** `#1385 =( A(...) B(...) C() );` —— 多子类型并列、无单一类型名。
   单类型正则整条**静默跳过**。本文件 **605 个**（= ID 空洞数），含全部装配变换。
   ★ 修好这一处后**实体计数已对齐（154708 / 0 缺失），但几何仍然是 0** —— 说明还有别的坑。
2. **嵌套括号引用**：`FACE_OUTER_BOUND('NONE', (#101436), .T.)` 的环引用嵌在子括号里，
   `refs()` 只处理 str 不处理 list 就漏整条 bound 链。
3. **编码**：名义 ISO-8859-1，法语名（`pieds sous la platine`）+ 中文占位标签交替。

> **铁律**：不要用自研解析器读复杂标准格式（STEP/IGES/DWG/DICOM…）。
> 当自研工具给出**否定性结论**（「文件坏了」「数据缺」）时，**必须先用参考实现复核**，
> 否则会把「工具的能力边界」误报成「数据的缺陷」。
> ⇒ 正确顺序永远是**先 OCCT 复核，再下结论**。

**★ 关键坑：不能只把 `reverse` 翻过来。** `homePose.gripper = 50` 必须反算出 **S6=90**（固件开机位），
反向映射下这两条约束**互相打架**：

| offset | θ=0 | θ=50(HOME) | θ=90 | 结论 |
|---|---|---|---|---|
| 130 | 130 ✅ | **80 ❌** | 40 ✅ | HOME 不是 90 |
| 140 | **140 ❌** 超上限 | 90 ✅ | 50 | 闭合端超限 |

⇒ **根因是关节限位 `0..90` 本身照旧（错）方向定的**，不是 offset 的问题。
**正解**：`offset: 140 / reverse: true`（`servo = -θ + 140`）+ 限位由舵机硬限位 40..130
**反算**得 **`10..100`**。三端点全自洽：θ=10→130(闭合) / θ=50→90(HOME) / θ=100→40(张开)。

## gripper「偶发不顺畅」排查（ADR D80 后的第二件事）—— 结论：**固件链路无缺陷**

**用户反馈**：方向已修好，但 gripper 开关**偶发不顺畅**，且"这个昨天解决过"（提交 caf402d）。

**协作口径（用户选定）**：我构建/烧录（烧录需确认）；诊断用 **WS 旁听 + 直连串口**；
修复范围 **只做 ① 消除忙等 + ② RX/TX 丢弃计数**，不做 ③（解析失败回 ERR PARSE）。

### 固件改动（`MeArm-Device`，已烧录 COM18 并校验）

| 文件 | 改动 |
|---|---|
| `bsp/uart.c` | `TX_BUF_SZ` 128→**256**；`uart_putc()` 去掉 `while (tx_full())` 忙等，改为**丢字节 + 计数**；RX ISR 环满时**计数**（原为完全静默丢弃）；新增 `uart_*_drop_count()` / `uart_clear_drop_counters()` |
| `bsp/uart.h` | 新增 3 条声明 |
| `core/cmd.c` | 新增 **`STATS [CLEAR]`** 命令 → `OK STATS rx_drop=N tx_drop=N`；`HELP` + 协议注释同步 |

**占用对比（零警告）**：FLASH 12582 → **12848 B**（39.0%→39.8%）；RAM 708 → **844 B**（34.6%→41.2%）。
RAM 增量主要是 TX 环 +128B。

### ★★ 实测结论：**链路层无丢字节**（这次没复现出缺陷）

真机 COM18，120 帧 × 2 条 SET，33ms 节拍（复刻前端 `MIN_SEND_INTERVAL_MS`）：

| 场景 | 发送 | 收到 | 含 S6 | ERR | 缺失 | rx_drop | tx_drop |
|---|---|---|---|---|---|---|---|
| gripper 扫动 120 帧 | 240 | **240** | 120 | 0 | **0** | **0** | **0** |
| gripper 全行程 120 帧 | 240 | **240** | 120 | 0 | **0** | **0** | **0** |

两轮独立复现结果一致。`STATUS` 回读 `S6=97` 与最后一条 SET 目标**一致**（固件确实接受了目标）。

⇒ **原先假设的链条**（`uart_putc` 忙等 → 主循环停读 RX → 环满静默丢字节）**在真机上不成立**。
本次改动仍有价值（把"偶发且零信号"变成"可读数的计数"），但**它没有修掉一个已证实的缺陷**。

### ★★ 最大的教训：**我自己的诊断工具才是误报源**（要长期记住）

`probe_gripper_link.py` 的 `--mode burst` 一度稳定报 **"缺 221 条 / 120 帧全部无 ACK"**，
看起来完美复现了缺陷。**全是工具自身的度量缺陷**，共 4 处：

1. **`_read_line()` 只在读到新串口字节时才可能返回一行**。一次 `read(256)` 拿回一大块后，
   其余留在 `self._buf`；下次调用若串口暂无新字节 ⇒ 空转到 0.05s 返回 `None`
   —— **尽管缓冲里还有 200 行**。`drain()` 的空闲判据被这个假 `None` 触发，提前收工。
   修法：进入循环前先查 `self._buf` 是否已含完整行，有就**直接返回、完全不碰串口**。
2. **`burst` 模式并没有"fire-and-forget"**：原实现里逐条 `wait_for`，等于把压力降到
   "发一条等一条"，还把迟到的 ACK 塞进 `others` 而 `report()` **从不打印 `others`**
   ⇒ 迟到的 ACK 被静默吞掉并计成"缺失"。
3. **只填 `ack1_line`/`ack2_line`，没填 `ack1_ms`/`ack2_ms`**，而 `report()` 的 missing
   统计读的是 `_ms is None` ⇒ burst 模式**恒定**报"全帧无 ACK"。
4. **板子复位后有两个吞命令窗口**（横幅前 / 横幅后各一次）。
   原 `_discard_banner()` 固定等 3.0s 且只读一行就 break ⇒ 横幅晚到就留在缓冲里污染后续；
   更糟的是 **DTR 边沿并非每次都触发复位**，所以"是否看到横幅"**不能**当就绪判据。
   正解：**重试探针**（反复发一条轻量命令直到收到回执）—— 就绪的定义是"能应答"。

> **纪律**：一个"高丢帧率"的读数**未必是缺陷**，可能只是测量窗口太窄 / 缓冲没排干。
> 能一票否决它的只有**独立的计数器**（`STATS`）。这与 SOUL 的
> "不许用推导量当独立判据"同源，也与本文件 §"自研解析器"那条同源 ——
> **工具的局限会被表现成数据的性质**。

### 板子复位后的「吞命令」窗口（独立可复用事实）

```
try0: ''                                  ← 窗口①（横幅还没出来）
try1: '[meArm] ... ready' / 'STATUS ...'  ← 复位横幅（~1.6s 才到）
try2: ''                                  ← 窗口②（横幅之后又吞一条）
try3..: 'OK STATS rx_drop=0 tx_drop=0'    ← 之后稳定
```
**不是固件缺陷**：主循环非阻塞（`cmd_poll()` 每轮都跑），是复位后 UART 的稳定窗口
（横幅由 `uart_puts` 在 `sei()` 之后立即打出，此时 RX 路径尚未完全就绪）。
