# 坐标系统与单位约定

> 本文是 ArmPilot 的**唯一坐标系权威文档**。任何涉及轴向、正负号、单位换算的问题，以本文为准。
> 相关实现：`frontend/src/robot/kinematics/coordinate.ts`（转换层）、`config/robot.yaml`（几何参数）。

## 1. 坐标系

**右手系，Z 轴向上。**

```
        Z (上)
        │
        │
        │
        └───────── Y (左)
       /
      /
     X (前)
```

| 轴 | 含义 | 正方向 |
|----|------|--------|
| X | 前后 | **+X = 正前方**（机械臂伸出方向） |
| Y | 左右 | **+Y = 左侧** |
| Z | 上下 | **+Z = 上方** |

右手验证：`X × Y = Z`（前 × 左 = 上）。

**为什么必须写死一套**：虚拟机械臂（Three.js）、FK、IK、真实机械臂（AVR 舵机）必须共享同一个
坐标系，否则会在业务代码里散落 `-x` / `90 - angle` / `180 - angle` 这类"补丁式转换"，
最终无人能说清到底哪一层翻转过。**本项目禁止此类散落转换**，见 §6。

## 2. 单位

| 量 | 单位 | 说明 |
|----|------|------|
| 长度 / 位置 | **mm** | `RobotModel.units === "mm"`，由模型校验强制 |
| 角度 | **degree** | 关节角、关节限位、舵机角、TCP 欧拉角，全部是度 |
| Three.js 场景单位 | **1 unit = 1 mm** | 见 §5 |

唯一例外：`kinematics/transform.ts` 内部矩阵运算使用**弧度**（数学库惯例），
进出该层时必须显式经过 `degToRad` / `radToDeg`，不允许隐式换算。

## 3. 运动学链规则（只需记住这一条）

```
   一根连杆沿「其近端关节坐标系」的 +Z 方向伸展 link.length，
   末端即为下一个关节的坐标系原点（再叠加该关节可选的 origin.position 附加偏移）。
```

因此 **`link.length` 是机构尺寸的唯一真值 —— 改一个数字，机构就变长/变短**，
不需要同步修改任何关节字段。

形式化表达（FK 唯一公式）：

```
T_joint = T_parentJoint · Tz(parentLink.length) · T(origin.position)
                              · R_eulerXYZ(origin.rotation) · R_axis(θ)
```

- `Tz(len)`：沿父关节坐标系 +Z 平移父连杆长度
- `origin.position`：可选附加偏移（默认 `[0,0,0]`，仅用于关节与连杆不共线的场合）
- `origin.rotation`：关节坐标系的**固定朝向**（intrinsic XYZ，度）
- `R_axis(θ)`：绕 `axis` 按右手定则旋转关节角 θ

### 关节角语义

**θ = 0 时，子连杆沿本关节坐标系 +Z 伸展。** 由此：

| 关节 | 轴 | θ = 0 的物理含义 | +θ 的方向 |
|------|----|------------------|-----------|
| `base` (J1) | `[0,0,1]` | 指向 +X（正前方） | 绕 +Z 逆时针 → 转向 +Y（左侧） |
| `shoulder` (J2) | `[0,1,0]` | 大臂**竖直向上** | 绕 +Y → 向 +X 前方倾倒 |
| `elbow` (J3) | `[0,1,0]` | 小臂**竖直向上**（**绝对**倾角 0° = 指向天顶） | 向前倾倒 —— 见下方 ⚠️ |
| `tool` | `[0,1,0]` | 固定关节，无自由度 | — |
| `gripper` | `[1,0,0]` | 夹爪完全**闭合** | 张开，铰轴沿工具系 X → 两爪沿 ±Y 分开 |

> ⚠️ **`elbow` 存的是"绝对倾角"，不是相对大臂的夹角。** 真机小臂由独立舵机经
> **平行四连杆**驱动，2026-09-12 实测：肩关节转 52.91° 时小臂绝对倾角只漂 10.08°
> （而相对角变了 −42.83°）⇒ 小臂角与肩角**解耦**。
> 模型用关节 `coupling` 表达：`relative = value + (−1) × shoulder`。
> 因此 `elbow` 的可达区间是 `108.44° … 141.86°`（**不含 0°**）——
> "小臂指向天顶"在真机上**不可达**。完整证据见 `docs/hardware-measurement.md`。

> ⚠️ 与原 spec 示例 yaml 的差异：spec 给的 `base.axis = [0,1,0]`、`shoulder.axis = [0,0,1]`
> 与其自身 §九「Z = 上下」的定义矛盾（那会得到一个水平面内的 SCARA 式机构）。
> 本项目按 §九 的坐标系语义取 `base = Z`、`shoulder/elbow = Y`。详见 `docs/decisions.md` D2。

### 零位与 HOME

| 位姿 | 含义 | 关节角 | 对应舵机 |
|------|------|--------|----------|
| **零位（ZERO）** | 关节空间原点（全 0）。⚠️ `elbow` 的 0° 真机不可达，实际会被钳到 `108.44°`（最竖直可达角） | 全 0 → 钳位后 `base 0 / shoulder 0 / elbow 108.4414852068 / gripper 0` | 见 §4 |
| **HOME** | 固件开机位（全部舵机 90°），已知安全位姿 | `base 0 / shoulder 0.8498937633 / elbow 112.6185771989 / gripper 50` | 全部 90° |

HOME 的数值由 **2026-09-12 实拍反解**得到（见 `docs/hardware-measurement.md`），
与 §4 的 `offset / scale` 严格自洽 —— 代入标定式回算恰好都是 90°。
HOME TCP = `(111.96, 0, 93.84)` mm。

## 3.1 IK 解算约定（Phase 5）

实现：`frontend/src/robot/kinematics/ik.ts`。IK 只输出关节角（`JointState`），
**只解定位三关节 `base / shoulder / elbow`**，绝不碰夹爪与标定（见 §4）。

### 解耦成两步

```
J1 = atan2(y, x)        ← 偏航：与高度无关，把三维降成矢状面内的二维
r  = hypot(x, y)        ← 矢状面内的水平半径

矢状面内 2R（枢轴 = 肩枢轴 (0, 0, 立柱高)）：
  L1 = 肩枢轴 → 肘枢轴            （大臂）
  L2 = 肘枢轴 → TCP               （小臂 + 手腕 + 夹爪）
  dr = r − 枢轴水平半径,  dz = z − 枢轴高度,  D = hypot(dr, dz)
  α  = ±acos((D² − L1² − L2²) / (2·L1·L2))      ← 相对肘角 ∠(θe − θs)
  φ  = atan2(dr, dz)                            ← 0 = 天顶，+ 向前
  θs = φ − atan2(L2·sinα, L1 + L2·cosα)
  θe = θs + α
```

### ⚠️ 与常见 meArm 推导的唯一差别：`elbow` 是绝对角

`θe` 解出来**就是**要写进 `JointState.elbow` 的值，**不要再叠加肩角**。
串联网里的局部旋转由 FK 的 `effectiveJointAngle()` 负责（`relative = θe − θs`）。
按"再叠加一次肩角"的常规写法会让机构立刻错位 —— 见 `docs/decisions.md` D18。

### 几何量不写死

`L1 / L2 / 枢轴高度` 全部在运行时从模型求导：把全部关节置 0 跑一次 FK，
机构即沿 +Z 竖直伸展，此时**相邻枢轴的间距就是矢状面内的等效连杆长度**，
天然把 `origin.position` 与 `tcp.offset` 一并算进去。当前机构求导结果：

| 量 | 值（mm） | 构成 |
|----|----------|------|
| `pivotZ` | 60 | `column_link.length`（立柱） |
| `L1` | 80 | `upper_arm_link.length`（大臂） |
| `L2` | 120 | `forearm_link.length` 80 + `tcp.offset.z` 40 |
| `reach` | `[40, 200]` | `[|L1−L2|, L1+L2]` |

> 注意 `L2` **不含** `tool_link.length`：TCP 的参考关节取的是 `tool`（不是 `gripper`），
> 所以手腕那 40mm 由 `tcp.offset` 而非 `tool_link.length` 贡献。
> 于是解析解为 `x = 80·sin(θs) + 120·sin(θe)`、`z = 60 + 80·cos(θs) + 120·cos(θe)` —— 
> 与 `frontend/tests/e2e/ui-smoke.mjs` 里的断言式逐位一致。

### 错误码

| 条件 | 返回 |
|------|------|
| `D > L1+L2` 或 `D < |L1−L2|` | `OUT_OF_WORKSPACE` |
| 目标方位角超出底座 `±60°` | `JOINT_LIMIT`，`joint = "base"` |
| 几何可达但两支解都越界 | `JOINT_LIMIT`，`joint` 指向越界最轻的那支所涉关节 |

失败信息格式对齐 `protocol/serial-v1.md` 的 `ERR JOINT base 95 (limit -60..60)`。
返回前 IK 会用 FK 自查残差（`residual`，mm），超出容差即抛错而非静默返回。

### 多解与"本机只有一支解"

平面 2R 有两支解，按相对肘角符号命名：`elbow-up`（`α > 0`，**HOME 所在支**）、
`elbow-down`（`α < 0`）。`prefer` 可选 `'elbow-up' | 'elbow-down' | 'nearest'`，**默认 `'nearest'`**
（按 `near` 当前状态就近选支，供 Phase 6 拖动避免翻肘；缺 `near` 时退化为 `elbow-up`）。

> **但本机结构上「肘向下」恒不可达**：由实测限位直接推出
> `elbow.limits.min − shoulder.limits.max = 108.4415 − 49.4549 = 58.99° > 0`，
> 即**相对肘角恒为正**。所以本机实际只有一支可行解（2000 组随机位姿中
> `elbow-down` 可行次数为 0），多解策略是为**将来换机构**预留的通用性，
> 当前不会触发翻肘。该不变量已被测试锁死（`tests/unit/ik.test.ts`）。

### 退化情况

目标落在偏航轴上（`r ≈ 0`）时方位角数学上不定：不报错，`J1` 取 `near`（或 `homePose`）并钳位，
结果里 `azimuthIndeterminate = true` 供上层知情。

## 3.2 末端目标与拖动交互（Phase 6）

### 三个量，别混

| 量 | 含义 | 来源 | 目标越界时 |
|----|------|------|-----------|
| `target` | **我想去哪**（mm） | XYZ 直输 / 鼠标拖动 / Jog | **照常保留**，让用户看到"差多远" |
| `commandJoints` | **实际去哪**（度） | `moveTo()` 的求解结果 | **逐位不变** |
| `endEffector` | `commandJoints` 的 FK 结果 | FK | 恒在机构量程内 |

`target` 与 `commandJoints` 的差就是"还差多远"，场景里表现为**把手球与 TCP 圆点分离**
（两者之间画虚线）。这是工作空间边界唯一直观的可视化方式。

### 目标越界时**不钳位**（硬规定）

目标不可达时只更新 `target` 与状态栏（`OUT_OF_WORKSPACE` / `JOINT_LIMIT`），
**绝不把关节推到限位边界**。理由有二：

1. 钳位会让工作空间边界从界面上"消失"，用户无法建立对机构能力的直觉；
2. 工作空间边界（球壳 `[40, 200]`）与关节限位**不是同一个约束** ——
   球壳边界上的点仍可能违反关节限位，钳位反而会造出一个"看似合法、真机做不到"的姿态。

### 拖动平面必须**冻结**

按住把手的那一刻（`pointerdown`）冻结两件东西，之后整个拖动过程不再改变：

| 冻结项 | 取值 |
|--------|------|
| 平面锚点 | 按下瞬间的 TCP（同时 `resetTarget()`，把起点吸附到真实末端） |
| 平面法线 | 由当时的平面模式决定 |
| 平面模式 | 一并冻结，拖动中途改下拉不影响进行中的这次拖动 |

| 模式 | 法线 | 自由度 |
|------|------|--------|
| `xy` | `(0, 0, 1)` | 只改 X / Y，Z 严格锁定 |
| `xz` | `(0, 1, 0)` | 只改 X / Z，Y 严格锁定 |
| `camera` | `−相机视线` | 三轴全自由 |

> ⚠️ **若每帧按当前 TCP 重建平面，会形成自反馈环**：目标变 → 关节变 → TCP 变 →
> 平面跟着变 → 鼠标与目标点之间永远无法收敛，手感表现为"飘走"。
> 冻结后平面与屏幕之间是**静态映射**，手感才跟手。

拖动期间 `OrbitControls` 必须禁用（否则变成一边转相机一边拖末端），
并用 `setPointerCapture` 保证指针移出 canvas 也不中断。

### 自由度"锁死"是**精确相等**

`xy` / `xz` 模式在求交后会把被锁分量**显式设回锚点值**，而不是"理论上相等、浮点上差 1e-15"。
因此测试可以直接断言 `target[2] === anchor[2]` —— 把"锁 Z"变成可验证的**定义**，而非数值巧合。

### 非目标驱动会同步 `target`

滑杆 / HOME / ZERO 属于"用户没有指定目标"，它们会让 `target` **跟随新的 TCP** 并清空状态栏，
否则幽灵标记会停在旧位置误报"未到位"。

## 3.3 传输层与闭环约定（Phase 7）

### 单向闭环，绝不互写

```
commandJoints ──节流──▶ Transport ──▶ 机械臂
                                       │
actualJoints  ◀──回推── Transport ◀────┘
```

- **下行只走 `commandJoints`**：所有改命令的路径（滑杆 / HOME / ZERO / `moveTo`）汇流到一处
- **上行只走 `actualJoints`**：Transport 回推的 `RobotState` 只写它，**绝不回写命令**

两边互相写就是 `命令 → 状态 → 命令` 的无限回环。这条不变量有测试锁死：400 点拖动轨迹中，
回推期间的 `commandJoints` **对象引用都没变过**（`tests/acceptance/transport-loop.test.ts`）。

### `actualJoints` 的写入者有两种，由 `transportDriven` 切换

| 状态 | 写入者 | 效果 |
|------|--------|------|
| 未接入（`false`） | 命令路径（`deriveVirtual`） | `actual ≡ command`，仿真立即跟随 |
| 已接入（`true`） | **仅** Transport 回推 | 拖动时滞后、松手后收敛 |

**为什么必须切换**：若接入后命令路径仍然写 `actual`，Mock 的滞后回推会被下一次命令
立刻覆盖 —— 误差永远显示 0，整条误差链路形同虚设。

断开连接时会把 `actual` **拉回** `command`：否则最后那次回推的滞后值会永久挂在面板上，
而此时已经没有任何 transport 再去驱动它收敛，显示的是一个假误差。

### 3D 场景渲染的始终是 `commandJoints`

虚拟臂画的是**命令的即时预测**（不滞后），`actualJoints` 只进状态面板。
两者分离才能回答"真机跟上了没有"这个 ArmPilot 的核心问题。

### 命令下发必须节流（尾沿合并）

拖动时每帧都会改命令（60fps ⇒ 每秒 60 条）。Phase 9 串口在 115200 + ACK 门控下不可能承受。
故取**尾沿合并**：33ms 内只保留最新一帧，**拖动结束时由 trailing 定时器补发最后一帧**
—— 少了这条补发，机械臂会停在半路。

实测：400 次命令变化最终只下发 10–80 条（`transport-loop.test.ts` 断言）。

### Mock 的物理约束是**故意**的

`MockTransport` 如实模拟的不是"接口"，而是"机械臂"：

| 模拟项 | 默认值 | 可观察到的现象 |
|--------|--------|---------------|
| 舵机有限角速度 | 240°/s | 拖动时 Actual 滞后；阶跃 40° 约 182ms 收敛 |
| 传输延迟 | 15ms | 命令送达前 Actual 一动不动 |
| 回推丢帧 | 0% | 拉高后机械臂照常运动，但上位机收不到状态 |
| 限位校验 | 开 | 越界回 `ERR JOINT ...` 且**位置保持不动** |

**丢帧只影响上报，不影响机械臂** —— 这是真实链路的行为，也是下位机自主性的体现。

> 若把 Mock 做成"零延迟等值回显"，链路结构虽然通了，但误差显示、收敛逻辑、丢帧容错、
> 限位拒绝**四条路径一条都没被验证**，全部推迟到 Phase 11 真机时第一次暴露。
> e2e 里有一条断言专门守着这点：设完滑杆**立刻**读数，Actual 必须明显滞后
> （实测 `cmd 39.9° / act 0.8° / 差 39.1°`）。

## 3.4 真实链路（Phase 8）：`WebSocketTransport` + Go 后端

```
commandJoints ──节流──▶ WebSocketTransport ──JSON──▶ Go 控制器 ──JR──▶ 假固件 / AVR
                                                          │
actualJoints  ◀──回推── …  ◀── joint_state ◀── …  ◀── STATE（舵机实际角 → 反算关节角）
```

§3.3 的四条不变量（单向闭环 / `transportDriven` 排他 / 只有命令进 3D / 尾沿合并）**一条都没变**。
变的是链路**真的存在**了，于是多出四条以前不存在的约束：

### 同一时刻只允许一条命令在途（ACK 门控 + latest-wins）

Phase 9 串口在 115200 + ACK 门控下不可能并发。故 Go 控制器里：

- 有命令在途时，新来的 `joint_command` **只覆盖"待发槽"，不排队**
- 排队会让拖动时命令堆积，回执永远在追历史的某个中间位置（用户看到"越拖越滞后"）
- 回执（`OK JR`）到达前不发下一条；超时（`ack_timeout_ms`）则上报并补发待发槽

### ⚠️ 链路精度 = 跟踪误差的可分辨下限（0.1°）

`JR` 只保留 1 位小数。前端内部是全精度浮点（HOME 位 `elbow = 112.6185771989`），
线上是 `112.6` —— **直接相减恒差 `0.0186°`**。

若不管它，面板会永久显示「跟踪误差 `0.02°`」且「正在逼近目标」永不熄灭：
**那是个假误差**，链路早已到位，只是双方用不同精度表述同一个位置。
所以误差必须在**线上精度**上定义：`wsProtocol.quantizeForWire()` 在比对前把命令归整到
`WIRE_JOINT_STEP_DEG = 0.1`，之后误差可精确归零；而 0.1° 以上的真实滞后照实上报。

### 断线重连必须**补发当前命令**

断线期间用户可能已经拖到别处。重连成功时若不补发，虚拟臂与实际臂会**永久错开，
而 UI 上看不出任何异常** —— 这是"看起来正常"里最危险的一类。

`transportBridge` 的处理：只在**重连**时补发（`hasConnectedOnce`），首次连接不补 ——
否则会无端占用一次节流窗口，改变 Phase 7 已锁定的时序契约。

> e2e 的验收方式很直接：杀掉后端 → 重启（新进程的 sim 从 HOME 起步）→
> 必须收敛回 `29.9°`。**没补发就会永久停在 HOME，这条断言必失败。**

### 模型真值在线互检（`hello`）

后端接入即推 `hello`，携带它读到的**限位 / 关节顺序 / 舵机通道 / 标定 offset·scale·reverse**。
前端与本地 `RobotModel` 逐项比对（容差 `1e-6`），不一致立刻告警（**但不断开** —— 链路仍可用）。

这是"标定表只有一份"这条铁律**唯一能被在线检验**的地方：两端读到不同的 `robot.yaml`
时会当场暴露，而不是等到某个姿态下发现机械臂动错了。

## 4. 关节空间 ↔ 舵机空间（标定）

```
Joint Angle  ──Calibration──▶  Servo Angle  ──▶  AVR(6/7/8/9) ──▶ 舵机
```

```
servo = reverse ? (-θ × scale + offset) : (θ × scale + offset)
```

| 关节 | 舵机 ID | 关节限位 | offset | scale | reverse | 关节限位映射到的舵机范围 | 固件硬限位 |
|------|---------|----------|--------|-------|---------|--------------------------|------------|
| base | S9 | −60 … +60 | 90 | 1 | false | 30 … 150 | 30 … 150 |
| shoulder | **S7** | −6.0936827341 … 49.454929245 | 88.776 | 1.44018 | false | 80 … 160 | 80 … 160 |
| elbow | **S8** | 108.4414852068 … 141.8582211436 | 359.61 | 2.39401 | **true** | 100 … 20 | 20 … 100 |
| gripper | S6 | 0 … 90 | 40 | 1 | false | 40 … 130 | 40 … 130 |

**关节限位与 offset/scale 是同一组实测反解的两个面**，映射后恰好铺满舵机硬限位，因此：
- 虚拟机械臂的可动范围 = 真实机械臂的可达范围，不会出现"网页能拖、真机动不了"；
- 「关节限位 → 舵机角」的越界检查（`ACTUATOR_REACH`）可以在配置阶段就拦住不可实现的参数。

数值来源（**2026-09-12 实拍反解，非推定**，完整证据见 `docs/hardware-measurement.md`）：

| 关节 | 舵机 | 实测增益（关节度/舵机度） | 锚点（舵机 90° 时） |
|------|------|---------------------------|---------------------|
| shoulder | S7 | 0.694（6–7 帧线性拟合，非线性明显） | 肩角 **+0.85°** |
| elbow | S8 | 0.4177（6 帧线性拟合，最大偏差 2.47°） | 小臂绝对角 **112.62°** |

| 假设（旧，已证伪） | 现改为 |
|--------------------|--------|
| S9 = 90 ⇒ 正前方 | 不变（实测吻合） |
| S8 = 100 ⇒ 大臂竖直 | **S7 = 90 ⇒ 大臂前倾 0.85°** |
| S7 = 80 ⇒ 小臂与大臂共线 | **S8 = 90 ⇒ 小臂绝对角 112.62°** |
| S6 = 40 ⇒ 夹爪闭合 | 不变（实测吻合） |

> 机构实际装向若变化，**只改 `config/robot.yaml` 的 offset / reverse / scale，不改代码**。
> 测量方法、精度与残余不确定度见 `docs/hardware-measurement.md` §4。

### ⚠️ 标定绝不进入 IK

IK 永远只输出关节角（`JointState`），绝不知道舵机、PWM、脉宽、通道号。
标定是它的**下游**。同理，若某个机械关节由两个舵机共同驱动，只需在 yaml 里给同一 `jointId`
写两条 actuator 记录，IK / UI / RobotState 完全无感。

## 5. 与 Three.js 的映射

| 项 | 做法 |
|----|------|
| 场景朝向 | `THREE.Object3D.DEFAULT_UP.set(0, 0, 1)`，在 `main.tsx` 中**创建任何相机/控制器之前**执行；`<Canvas camera={{ up: [0,0,1] }}>` 再兜底一次 |
| 单位 | `SCENE_UNITS_PER_MM = 1`，即 1 场景单位 = 1 mm，**不存在任何隐藏缩放** |
| 地面网格 | drei `<Grid>` 默认位于 XZ 平面，需 `rotation={[Math.PI/2,0,0]}` 才能落到世界 XY 平面（Z=0） |
| 关节 | 一个关节 = 一个 `THREE.Group`；`group.position = (0,0,parentLink.length) + origin.position`；`group.quaternion = qEulerXYZ(origin.rotation) · qAxisAngle(axis, θ)` |

因为单位与朝向完全一致，**FK 算出的 XYZ 与屏幕上模型的实际世界坐标可以直接逐值比较**，
这就是 Phase 3 验收条件（误差 < 0.1 mm）能够成立的原因。

实测结果（200 组随机关节状态）：

```
末端位置最大误差       8.673e-14 mm
关节坐标系矩阵最大误差 8.527e-14
```

即浮点噪声级 —— 屏幕上的机械臂**就是** FK 算出来的那一台。

## 6. 禁止事项

❌ 在业务代码中出现 `-x` / `-y` / `90 - angle` / `180 - angle` 之类的散落转换

✅ 正确的落点（按优先级）：

1. `config/robot.yaml` 的 `joints[].axis` —— 轴向不对
2. `config/robot.yaml` 的 `actuators[].reverse` / `offset` —— 真实机构装反 / 零点不同
3. `frontend/src/robot/kinematics/coordinate.ts` —— 真正跨坐标系时才在这里加转换

❌ 把**越界的目标点**静默钳位到工作空间边界再驱动关节

✅ 正确做法：目标越界时 `target` 照常保留、`commandJoints` 逐位不变，
由状态栏报 `OUT_OF_WORKSPACE` / `JOINT_LIMIT`（见 §3.2 与 D20）。
球壳边界 `[40, 200]` 与关节限位**不是同一个约束**，钳位会造出"看似合法、真机做不到"的姿态。

❌ 在拖动过程中按当前 TCP 重建拖动平面

✅ 正确做法：`pointerdown` 时冻结平面（锚点 + 法线 + 模式），整个拖动过程不再改变
（见 §3.2 与 D21）。否则形成 `目标变 → 关节变 → TCP 变 → 平面又变` 的自反馈环，手感会"飘走"。

❌ 在 Transport 的回推回调里回写 `commandJoints`

✅ 正确做法：回推**只写** `actualJoints`（见 §3.3 与 D23）。回写命令即 `命令 → 状态 → 命令`
的无限回环，且会让"用户意图"被"机械臂实际位置"覆盖。

❌ 把 `MockTransport` 做成零延迟等值回显

✅ 正确做法：如实模拟有限角速度 / 传输延迟 / 丢帧 / 限位拒绝（见 §3.3 与 D24）。
理想回显下 `actual ≡ command`、误差恒 0，误差显示与收敛逻辑**一条都没被验证**，
全部推迟到真机时第一次暴露。
